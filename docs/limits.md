# What we can't do yet — the honest limits

This is the single place where every known limit of the tool is written down in plain
words. It is **the source of truth**: the QA report published on every CI run embeds
the table below verbatim, so a limit recorded here reaches every reader automatically
and a limit *not* recorded here is invisible — which is exactly why it belongs here
first.

The rule behind it: **we never claim a file is untraceable unless we have actually
proven it.** Where a limit is a law of physics, we say so instead of pretending it is
solved. Where our own claim turned out to be broader than our evidence, we write that
down too, rather than quietly narrowing it.

Status key: ✅ solved · 🟡 bounded (small, measured, documented) · 🔴 open (known gap,
not yet fixed) · ⚪ out of scope (impossible, or outside the threat model) ·
🔜 planned.

| # | The honest limit (plain words) | What we do about it | Status |
|:-:|---|---|:--:|
| **1** | Even after every tag is deleted, the *way* a file was compressed leaves a hidden signature that can hint which app, phone or program made it. | We re-save through **one standard encoder** so every file we produce shares the same signature. For **PNG** and **FLAC** this costs **nothing at all** — identical pixels, identical audio, right down to the last bit. **JPEG** and **MP3** need a re-recording that costs a little quality, because their signature is baked into the compressed data rather than sitting in a separate layer. For MP3 it is proven against a genuinely *different* encoder, not just a different program using the same one. | ✅ **Solved** |
| **2** | Our "every file comes out looking the same" promise is **not one single group**. Low-quality-rate audio can't legally use our standard setting, so it comes out at a different one — a handful of groups, not one. Someone can see *which* group a file belongs to. | **Deliberate, and measured.** The group is decided by the recording's own sample rate, which we **preserve on purpose** — changing it would alter the audio, and keeping the sound untouched matters more. What must not leak is *who made the file*, and that is tested **inside every group separately**: at both 44.1 kHz and 22.05 kHz, no producer can be told from another after a full rebuild, in the file's structure **and** in its sound. The low-rate group is the **weaker** of the two results — both are indistinguishable from guessing, but it sits closer to the line, and a smaller earlier version of this test disagreed between two machines. We enlarged it until the answer stopped moving, and report the weaker case as weaker. | ✅ **Solved per group** |
| **3** | Some unusual audio files we **refuse to process at all**: older Layer II audio wearing an `.mp3` name, and files using a rare "free-format" bitrate. | The tool **fails closed** — it stops rather than write a file it cannot fully vouch for. Nothing leaks, but the user gets no output. Broader format support is planned. | 🟡 **Safe but incomplete** |
| **4** | Making a file untraceable means **re-recording** it, and that always costs something: a high-quality audio file loses some quality, and a very small file can come out several times **larger**. | An unavoidable trade of this approach, stated up front rather than hidden. The alternative — keeping the original audio untouched — is exactly what leaves the traceable signature in place. | 🟡 **Bounded trade-off** |
| **5** | Every camera sensor leaves a faint, unique **noise pattern baked into the pixels** (PRNU). Audio has the same problem: every **microphone and room** leaves a fingerprint, and mains electricity hums at a frequency that can date a recording. | These live **in the picture and in the sound itself**, not in the metadata — removing them would destroy the content. They are a known limit of **every tool that exists** and sit outside our medium-tier threat model. We document them openly. | ⚪ **Out of scope** |
| **6** | A **more sophisticated investigator** than the one we built might still succeed. Our audio test inspects the sound's frequency profile; published research also inspects the encoder's internal number-crunching, which we have **not** tested against. | We report what we measured and what we did not. We do **not** claim to survive attacks we never ran — the untested methods are named so the gap is visible rather than implied away. | 🔴 **Untested** |
| **7** | A second style of audio VBR header used by some encoders (Fraunhofer's **VBRI**) is **not recognised**. We had written that such files are refused. **They are not** — checked on 2026-09-24: the light clean accepts one and passes the header through unchanged, encoder version and all. | **Narrowed from an overclaim.** The header is an encoder trace of the same kind as the LAME tag the light clean already keeps on purpose, so no tag or personal field leaks through it. The deep clean re-records the audio and the header is gone (checked the same day). Recognising it — so it is at least reported, and removed at the levels that remove LAME's — is on the roadmap. | 🔜 **Planned** |
| **8** | We currently handle **JPEG, PNG, MP3, FLAC, M4A, PDF, Word (.docx), iPhone photos (HEIC), video (MP4, and the QuickTime MOV every iPhone records) and camera RAW from Canon (CR2 and CR3), Nikon (NEF), Sony (ARW), Fujifilm (RAF), Olympus (ORF), Panasonic (RW2) and iPhone ProRAW (DNG)**. Both documents are cleaned at all three levels, with the *fingerprint* not fully defeated at any of them, though Word's strongest level narrows it to a single clue. | HEIC, video and camera RAW are at the light level only so far. Next, on the same tested foundation: program files and archives. Each ships only when its differential tests pass. For PDF specifically, what is left is not a missing feature but a measured floor; see the rows below. | 🔜 **Planned** |
| **9** | A cleaned file is **recognisably cleaned**. Everything we produce comes out in the same standard shape, so someone can tell a scrubber was used — they just cannot tell *which program, phone or camera* made the original, or what was removed. | Unavoidable, and the point: looking identical to every other cleaned file is precisely what makes yours untraceable. Hiding that a file was cleaned is a different problem from hiding where it came from, and only the second one is what this tool promises. | ⚪ **Inherent** |
| **10** | For **M4A** files, if the original recording was made at a different quality setting, a faint trace of that earlier setting survives — not in the sound any more, but in the **file size**. | **Measured, and narrowed to one channel.** A test reading the original's quality from the sound alone is right **88%** of the time on an untouched file and drops to a **coin flip** after our rebuild. Files from the same original come out **byte-for-byte identical**. What is left is a ~1.4% size difference. Our test holds the audio constant, which makes size an unusually clean clue; among real files of varying length it is far weaker. Padding every file to a fixed size would close it, at the cost of bigger files — a trade we state rather than make quietly. | 🟡 **Bounded — one channel left** |
| **11** | Our safety check that “the audio still sounds the same” cannot be a simple sample-by-sample comparison. Some formats (AAC) deliberately rebuild noisy sounds — rain, applause, cymbals — rather than copying them exactly, so an honest re-recording can look very different sample-wise while sounding identical. | The check now asks two questions: are these still clearly the same recording, and does the energy across pitch and time match what a listener hears? **Both** must hold. Measured: real music-like noise passes, while two *different* noise recordings are still correctly rejected — the case a loudness-only check would wave through. | ✅ **Solved** |
| **12** | One piece of our evidence **cannot be re-run automatically**: proving that two different AAC encoders are indistinguishable needs Apple's encoder, which only exists on macOS. | The automated build reports that measurement as **not measured** rather than repeating a number it did not compute. The result stands, with the platform it was measured on named. | 🟡 **Measured, not automated** |
| **13** | **Blacking out text in a PDF is not the same as removing it.** If someone drew a black box over a paragraph, the words are still in the file underneath and can be read straight back out. Our cleaner does not fix that, and it never claims to. | A **different problem** from the one this tool solves, and the most misunderstood one in the format. What we *do* remove completely is the document's **edit history** — every earlier draft a PDF keeps inside itself, which is the leak behind most published "redaction" disasters. A warning tool that flags likely blacked-out text is planned; it will report, never silently "fix". | 🔴 **Not our problem to fix, but users must be told** |
| **14** | **Fonts and colour profiles carried inside a PDF keep their own small print.** An embedded font still says who made *the font* and when it was built; a colour profile still carries its name and copyright ("Generic Gray Gamma 2.2 Profile — Copyright Apple Inc."). | Measured, not assumed. These name the **font foundry and the operating system**, not the person or the document — so what leaks is roughly "this came off a Mac", not who wrote it. Removing them means rebuilding the font program and the colour data, which risks changing how the page looks; that belongs to the next fidelity level, where we can measure the cost. The colour-profile *header* — the parts naming the device and the creation date — is already wiped, and the same applies to wide-gamut JPEGs. | 🟡 **Bounded — narrows to platform, not person** |
| **15** | Some PDFs we **refuse to process at all**: encrypted ones, digitally signed ones, files with attachments, XFA forms, files with junk before the header, and "hybrid" files that carry two conflicting internal indexes. | The tool **fails closed** — it stops rather than write a file it cannot fully vouch for. Each refusal has a reason: a signature is destroyed by any rewrite, and quietly handing back a broken signature is worse than saying so; an attachment is a whole document of its own and needs its own cleaning pass; a hybrid file can show two *different* documents to two readers, so "the document" isn't even well defined. Each is on the roadmap. | 🟡 **Safe but incomplete** |
| **16** | **A PDF still names the program that typeset it, at every cleaning level.** Once the tags are gone, where each letter sits on the page, where the lines break and which letters were embedded still identify Chrome from Word from Preview. | **Measured across five real producers, not assumed.** The deep clean closes half of it outright — every instruction that paints the page is rewritten through one writer, and four of the five come out identical on it. The other half cannot change without re-typesetting the document, which would change what the reader sees. It is the same kind of limit as camera sensor noise: named as a floor, not left as an unfinished job. | 🔴 **Open — floor, not a gap** |
| **17** | **Flattening a PDF to pictures does not make it anonymous either**, and it costs the document its selectable text — it can no longer be searched, copied from, or read aloud by a screen reader. | **We attacked our own output rather than claiming the win.** A program reading only the shape of the ink names the producer on **every page**, and still does when the page is rendered so coarsely the text is unreadable — the clue is the margins and the width of the text block, which no amount of blurring touches. So the mode is offered for what it does do (it removes every structural trace) with its real cost stated first, and its fingerprint result published as a failure. | 🔴 **Open — measured, not evaded** |
| **18** | **The deep clean makes PDFs about a third bigger** (measured: 448 KB → 590 KB on a real 10-page report), and file size is itself one of the clues we report as leaking. | Stated as a real cost rather than a cosmetic one. It grows because every stream is unpacked and repacked with no shortcuts, and because absolute letter positioning is more verbose than the shorthand a producer writes. | 🟡 **Bounded trade-off** |
| **19** | **A Word document with tracked changes or comments is refused, not cleaned.** If someone left "track changes" on, the earlier wording and the reviewer's name are still in the file, and we stop rather than touch it. | This is a **deliberate refusal, not a missing feature.** Those edits are *content*: with markup switched on, a reader sees them on the page. Deleting them would change what the document says, which is the one thing this tool promises never to do — so quietly "cleaning" them would be a worse failure than declining. The tool says why and writes nothing. Accepting all revisions first, in Word, produces a document we will clean. A deeper cleaning level that can make that decision safely is planned. | 🟡 **Safe but incomplete** |
| **20** | **Bookmark names and web links inside a Word document survive.** A bookmark can be named after a person or a project, and a link can point at an internal file share. | Removing them would **break the document**: a table of contents, a cross-reference and a hyperlink all find their destination *by that name*, so deleting it turns working links into dead ones. One exception is removed, because nothing points at it: `_GoBack`, the invisible marker recording where the cursor was when the document was last saved. Everything else that survives is **listed back to the user by name** rather than quietly left in. | 🟡 **Bounded — reported, not hidden** |
| **21** | **The light clean still hints at which version of Word made the file.** Word writes a list of technology names at the top of each internal file, and that list has grown with each release — so the set of names roughly dates the program. | **Now fixed at the deeper clean, and the row is kept rather than deleted** so the difference between the two levels stays visible. The light clean only deletes, so it cannot touch the list; the deep clean rewrites every internal file and the names go with it. What leaked in the meantime was approximately "made by Word 2010-or-later", never who wrote it. | ✅ **Solved at the deep clean** |
| **22** | **A claim we had been repeating turned out to be wrong.** This project inherited from published research that Word's hidden "editing session" identifiers survive every cleaning tool, MAT2 included. Measured on our own documents, **they do not** — MAT2 removes them. | Corrected rather than quietly dropped, because the *useful* version of the finding is sharper than the original: the identifier the research named has been fixed upstream, and a **different set that nobody names has not**. Word stamps a hidden id on **every paragraph**, and those ids **travel with a paragraph when it is pasted into another document** — so two documents can be tied to one source. MAT2 leaves all of them; we remove them. The one tool that cannot help here at all is ExifTool, which **cannot write Word files** and says so. | ✅ **Solved (and the claim corrected)** |
| **23** | **A Word file can carry a small picture of its own first page**, and that picture may be **out of date** — showing a paragraph that has since been deleted. | We **remove the picture entirely**. MAT2 cleans the picture's own hidden data but keeps the picture, which is defensible right up until the moment it is stale — at which point the file is showing content the document no longer contains. That is the same family of problem as a PDF's buried earlier drafts, and it is solved the same way: remove it rather than tidy it. | ✅ **Solved** |
| **24** | **The deep clean accepts tracked changes and removes comments.** If a Word document was still under review, the reviewer's suggested wording, their name, and the comments in the margin are all resolved away — the document becomes the version that would print. | **A deliberate trade, stated before the level is offered rather than after it is used.** Those edits are content: with markup switched on, a reader sees them. The light clean therefore **refuses** such a document rather than touch it, and the deep clean **accepts** the changes as the author intended and says so. What cannot be recovered afterwards is the review history — so a document you still need to review should be cleaned at the light level, or reviewed first. | 🟡 **Bounded trade-off** |
| **25** | **A cleaned Word file still says which program wrote the document**, even after every internal file is rewritten. Which parts a program emits, which styles it defines, what settings it records and how it builds a paragraph all differ between Word, LibreOffice and everything else. | **Measured across four producers, not assumed.** The deep clean closes exactly half of it — the *spelling* of the markup (namespace names, tag style, punctuation of the header line) is rewritten through one writer and stops separating anyone. The other half is *substance*: it cannot change without changing the document itself. That is the same kind of limit as the letter positions in a PDF, or camera sensor noise: named as a floor, not left as an unfinished job. | 🔴 **Open — floor, not a gap** |
| **26** | **The strongest Word clean re-types the document through a different program**, so fonts can substitute and spacing can shift. It is the only level that does not preserve the page exactly. | **The trade is stated before the level is offered.** It exists because the previous level cannot remove what a program's *choices* say about it — which styles it defines, which settings it records — and only rebuilding the document through one program can. **We cannot currently measure the cost**, and say so rather than claiming there is none: our check renders the document through the same program that rebuilt it, which is that program grading its own homework. The real cost shows up on opening the file in Word, and Word cannot be driven by a script on any platform. Use the lighter levels when the page must stay exactly as it is. | 🟡 **Real cost, honestly unmeasured** |
| **27** | **Even after rebuilding a Word document through one program, a trace of how the *original* was made survives** — the styles the source defined are carried through rather than rebuilt. | **Measured, and narrowed to a single clue.** The rebuild collapses almost everything: which parts exist, which settings are written, how paragraphs are built all become the rebuilding program's, identically, for every file. What is left is one list, and it describes the document's **origin**, not the program that handed us the file. It is the same kind of leftover as a re-recorded audio file remembering its first recording's quality setting. | 🔴 **Open — narrowed to one clue** |
| **28** | **The report printed after each clean shows only what *this tool* can see**, and it prints the very values it removed. | Two things stated rather than assumed. First, "nothing listed" means *we found nothing*, never *the file was clean* — a hiding place no format handler models is missing from the report for the same reason it is missing from the clean. That is why every report now ends with a reading by **ExifTool, a different program**, including the exact command to repeat it yourself: our own account of our own work is not evidence, and where the two disagree the report says so and tells you to treat the clean as incomplete. Second, the report is a disclosure: an author's name and a GPS position that were inside a file end up on the terminal, and in the log if the output is redirected. Values are shortened, `--no-verify` skips the second opinion, and `--no-report` turns it all off. | 🟡 **Useful, with both edges named** |
| **29** | **Cleaning an already-cleaned file is free at the light levels and costs quality at the strongest one.** Running the deep clean twice re-records the file a second time. | **Measured, and the two halves behave differently on purpose.** Every bit-preserving and lossless level is a **fixed point**: clean a cleaned file and you get the identical file back, byte for byte, on all seven formats — which is also the proof that the first pass left nothing behind for a second one to find. The strongest level re-encodes, so a second pass is a second generation of loss, exactly as re-saving a photo twice would be. **Clean once, from the original.** A pipeline that cleans a file at each of several stages is quietly degrading it. | 🟡 **Fixed point where it matters; stated where it isn't** |
| **30** | **An iPhone photo carries a description of its own subject**, separate from the camera data everyone knows about. Apple ships a 58 KB block — 3–5% of the file — recording **whether there are people in the frame, how much of it is skin, and a small map of where they are**. | **We remove it**, along with the depth maps and person mattes stored beside the picture. It is worth naming because it is a different kind of thing from the rest: not a fact about the camera but a judgement a machine made about *what the photo is of*, computed on the phone and shipped inside the file. It is not a secret — ExifTool has always been able to show it — but nobody looks, and a photo you send a stranger should not come with a note saying how many people are in it. | ✅ **Removed** |
| **31** | **Removing the depth maps and mattes changes what some apps can do with a photo.** Portrait-mode relighting and background replacement use them. | A deliberate trade, and the reason it goes the way it does: those extra images are derived *from the subject* — one of them is literally a map of where the people are. A privacy tool should not ship that quietly, so the default removes them, the report says so by name, and the photo itself is untouched. **One is kept** — see the next row. If you need the others, keep the original. | 🟡 **Bounded trade-off** |
| **32** | **One extra image inside an iPhone photo is deliberately kept: the HDR brightness layer.** Without it the photo still opens and still shows the same picture, but on a phone or monitor that supports HDR it renders flat instead of bright. **Our own automatic check cannot see this** — the decoder we test with ignores that layer entirely, so a version of the tool that threw it away passed every pixel test we had. | **Kept on purpose, and the reasoning is written down rather than settled by taste.** Unlike the mattes, this layer says nothing about the *subject*: it is a half-size brightness map of the very pixels we are preserving, and it is part of how the photograph looks. Because our check is blind to it, the decision could not be made by running a test — so it is recorded here, where a future change to it has to argue with something. The cost of keeping it: a differently-compressed copy of the same scene stays in the file, which is one more place the camera's encoder signature appears. | 🟡 **Bounded — kept deliberately, untestable here** |
| **33** | **A cleaned iPhone photo still says which software wrote the file.** Not which phone or which person — but the brand stamped in the header, the order of the internal tables, the widths of the fields in its address table and the file's size are all the writing program's choices, and our only cleaning level for this format preserves every one of them. | **Measured across three container-writer profiles wrapping byte-identical picture data**, so the separation is the writing software and not the photo. This is what a bit-preserving level *is* — it relocates data and changes nothing else — so the result is published as a failure with each leaking feature named, and that list is the specification for the deeper level that would close it: one standard header, one table order, one set of field widths, items renumbered, with the picture untouched. The same method that was used for PDF: measure which channel leaks before designing the fix. | 🔴 **Open — measured, and the fix is specified** |
| **34** | **Every iPhone video measured keeps a second, forgotten copy of its location**, apart from the one any tool shows you. The camera writes its information (exact GPS, phone model, software version, recording time) once more every ten seconds of filming, into a part of the file no video player reads. Clips shorter than ten seconds put the copy at the very end of the file instead. We found it in all six iPhone clips we measured, and the same thing on a Mac (computer model, macOS version, time) in every screen recording. | **We remove it.** Rather than deleting known fields, the light clean rebuilds the video data from only what the player actually uses, so leftovers like this are never written in the first place. It matters because the usual tools miss it: **ExifTool's standard clean leaves the coordinates in the file and then reports it as having no GPS at all**, and MAT2 refuses iPhone videos (renamed to get past that, one crashed and left an empty file). An automated test re-checks the ExifTool result on real clips, so this row goes stale loudly if that ever changes. | ✅ **Removed** |
| **35** | **An iPhone video carries a running description of the people in it.** Beside the picture and sound it records, for most frames, **where each detected face is, which way it is turned, and an ID linking the same face across frames**, plus a unique serial number for the recording itself. | **We remove all of it**: six hidden tracks per iPhone clip, including the per-frame face boxes that ExifTool's standard clean leaves in place. Like the photo row above (#30), it is not a fact about the camera but a machine's judgement about *who is in the video*, and it has no business leaving the phone with the file. | ✅ **Removed** |
| **36** | **A video cleaned at the light level can still name the program that compressed it.** Some encoders write their name, version and every setting *inside the video stream itself*; WhatsApp's does, in every video it sends. The light clean keeps the video bit for bit, so that signature stays. | **Reported, not hidden.** The report says “kept” and names the encoder whenever it finds one. It is inside the picture data rather than in the metadata, the same situation as the MP3 encoder tag (#1). Removing it without re-compressing looks possible, because it sits in a separate block the player skips, but that is **not measured yet**, so it is not claimed. | 🔴 **Open** |
| **37** | **A cleaned video still shows which program wrote the file** — not which camera, not which person, and none of your content. | **Measured across four producers, one of them a genuinely different program rather than another setting of the same one.** Four things give it away: the four-letter brand stamped at the front, the list of standards the file claims to follow, the order the major sections are written in, and whether the index sits before or after the video so it can start playing while it downloads. Five other clues that did separate the same four producers are **closed**: the padding, which sections exist, the track labels, the width of one length field, and whether timestamps were written at all. The four that remain are the specification for the deeper mode, which is not built — and its row says *not tested* rather than guessing. | **38** | **Very large videos need a lot of memory.** The tool holds the whole file in memory while it works, plus the cleaned copy: measured at **about 2.1 times the file size** for video (113 MB for a 54 MB clip), and **about 4 times** for M4A audio. A 4 GB video needs roughly 10 GB free. | **Checked before anything is read.** The tool works out what the file needs from its size and the measured factor for its type, compares that with the memory the machine has free right now, and if it does not fit, refuses at once and says both numbers — rather than starting a scrub that ends minutes later in swapping or a crash. Video used to need 3.1 times the file: a redundant copy of the output was removed on 2026-10-04. Processing large files in pieces (streaming), so memory stays flat at any size, is the hardening work scheduled for November. | 🟡 **Bounded — checked up front** |
| **39** | Some videos we **refuse to process at all**: *fragmented* files (the style used for streaming and by some screen recorders), videos whose picture or sound lives in another file, videos with subtitle, caption or timecode tracks, **encrypted (DRM) videos**, and a rare compact form of the internal size table. | The tool **fails closed**, as with #3 and #15. | **40** | **The light clean can make a PDF about a tenth bigger** — but only when the original packed its internal pieces together to save space. Measured on a one-page CV: 44,620 → 49,344 bytes, **+10.6%**. | **Measured, and narrowed to its cause rather than reported as "PDFs grow".** A PDF may bundle many small internal objects into one compressed block; we write each object on its own, so a file that used one block grows and a file that did not barely moves. | **41** | **A bug we shipped: cleaning an Apple-muxed audio file produced a file that played as noise.** Any `.m4a` written by Apple's own muxer — a Voice Memo, anything exported by an Apple app — came out of the light clean sounding like static. | **Found by building the video format, not by a bug report, and fixed.** Apple writes the media block's length in a wider field than it needs; we assumed the narrow one, so every pointer into the sound ended up 8 bytes out. Both now exist: the length is read rather than assumed, and the tool follows every pointer from input to output and refuses to write a file whose pointers moved. | ✅ **Fixed** |
| **42** | **Cleaned video and audio files no longer say which program wrote them — at the cost of all looking alike.** Every track in a media file carries a short label naming the software that made it; Apple writes `Core Media Video`, ffmpeg writes `VideoHandler`. Blanking it means every file we produce carries an identical block there, which marks a file as *cleaned by something* — but never as cleaned *from what*. Leaving it would say "a Mac made this", which is worse. The blanked block is declared to our own fingerprint check rather than hidden from it, and a test asserts the declaration contains nothing else. | 🟡 **Bounded trade-off** |
| **43** | **Video and iPhone photos have only the light clean.** The deeper two modes do not exist for them. | **Said in the table rather than implied by silence.** Until this was fixed the report quoted a cost for those modes — "deep clean: costs you nothing at all" — for file types that do not offer one, which invited a reader to pick something unavailable. Those cells now read *not built for this file type yet*. What a deeper mode would do is written down rather than left open: rewrite the container through one single writer so every file comes out looking the same. | 🟡 **Bounded — stated, not implied** |
| **44** | **How much we can see of a video's fingerprint depends on the machine doing the measuring.** Two of the nine clues only become visible when a second, non-Apple-vs-Apple pair of programs is compared. | **Stated rather than smoothed over.** The common open-source tool writes the same track labels, the same four-letter brand and the same header width in *every* configuration, so comparing it only against itself cannot show that those clues exist at all. Adding Apple's own muxer — available only on a Mac — makes them visible. Our automated checks run on Linux, so the published comparison there is against a **strictly smaller** set of clues, and the result says which programs it compared. ## Where the evidence lives

<!-- RESIDUALS:BEGIN -->
- **How these verdicts are decided:** a one-sided binomial test against chance (alpha 0.10), not a fixed accuracy margin. The margin came first and was wrong: on 18 trials the standard error is ~0.12, so it turned sampling noise into a verdict and the same experiment landed on opposite sides on macOS and Linux. Every peer set now runs 36 trials per condition and reports its p-value.
- **DQT (JPEG quantization tables):** the F1/F2 fingerprint source — neutralised at F3 via a single standard encoder.
- **LAME/Xing header + bitrate contour (MP3):** the audio equivalent — survives F1, normalised at F3.
- **FLAC block size, framing and vendor string:** survive F1, normalised at F2 with **bit-identical audio** (STREAMINFO's MD5 of the unencoded samples proves it). The vendor string ("reference libFLAC…", "Lavf…") names the encoder outright but sits in a metadata block, so unlike MP3's LAME tag it costs nothing to remove. FLAC and PNG are the two formats where A2 is free.
- **Our own canonical form:** a scrubbed FLAC carries exactly one metadata block, so `fLaC` + the STREAMINFO header is constant across outputs; the MP3 canonical LAME header is the same kind of constant. Recorded in each matrix's `excluded` block and as limit #9 — it marks a file as scrubbed, never as scrubbed-from-what. Two earlier candidates were removed rather than excused after the fingerprint guard caught them: a fixed empty Vorbis comment and 8 KiB of fixed zero padding.
- **Cross-engine audio trace (MP3):** measured, not assumed. A classifier that identifies the source encoder from the sound alone scores **0.89 on untouched and F1 files and 0.53 after F3** (p=0.43, n=36 — not significantly above chance). Peer set includes `shineenc`, an encoder that is not libmp3lame. Scope: frequency-profile features; MDCT-domain classifiers untested (limit #6).
- **Anonymity groups (MP3 F3):** the standard 192 kbps setting is illegal for MPEG-2 sample rates, so those files emit at 160 kbps instead — separate groups (limit #2). Producer-anonymity is verified **within each group**, in header space (E-LAME, both rates pass) and in audio space (E-ENGINE: 44.1 kHz 0.89 → 0.53 at p=0.43, 22.05 kHz 0.94 → 0.58 at p=0.20, n=36 per group, chance 0.50). The group boundary follows the source's sample rate, which is content, not a producer trait.
- **M4A audio-space residual (E-M4A-AUDIO):** the source's own quality setting is recoverable from the sound at **0.88 on unscrubbed and copy-tier files, falling to chance (0.50) after F3**; same-source producers become byte-identical. Engine identity (ffmpeg AAC vs Apple AAC) is **not separable even unscrubbed** (0.56) — those two encoders are near-twins spectrally (99.5%-energy bandwidth 15075 vs 15427 Hz at the same bitrate), so this corpus cannot answer the engine question either way, and says so rather than counting a weak control as a pass (limits #10, #12).
- **Perceptual gate, two-stage:** AAC rebuilds noise rather than copying it, so waveform correlation alone refuses legitimate scrubs — measured 0.86-0.90 on noise through AAC versus 0.998 for MP3 on the same material. The gate now requires strong waveform correlation OR (still-strong correlation AND a matching time-frequency energy envelope). Both parts are needed: envelopes alone accept two different noise recordings, waveforms alone reject good AAC (limit #11).
- **PRNU (sensor noise) / microphone + room response / mains hum:** structural impossibilities; documented, out of scope (limit #5).
- **M4A muxer layout vs coded audio:** two producers in one file. F2 normalises the layout (box order, brand, `free` slack) losslessly; F3 additionally collapses same-source producers to byte-identical output. The primary-encoding trace from a differently-encoded original survives both, and is recorded as an open residual (limit #10) because no audio-space classifier has been run for M4A yet — the MP3 E-ENGINE treatment is what would settle it.
- **Primary-quantization estimate:** the bounded "was re-saved" hint after F3 — reveals nothing about original metadata.
- **PDF incremental-update history:** the format's own edit mechanism is *append*, so every earlier draft stays in the file and opens as a document if you truncate at an earlier end-marker. Closed by rebuilding the file from the object graph rather than appending — measured (E-PDF-HISTORY) with three independent attacks: revision rollback, raw carving, and an object ledger that separates *superseded* definitions from *orphaned* ones. A plain rewrite that strips nothing already recovers nothing, so the rewrite and the scrub are measured separately and neither takes credit for the other.
- **PDF producer channels, split in two:** the **serializer** (object order and numbering, xref style, the binary header comment, `/ID`, `/Length` conventions) and the **layout engine** (content-stream operators, number precision, font subsets, glyph geometry). F1 normalises the first by writing the bytes itself; the second is untouched at F1 and only partly normalisable at all — glyph positions and subset composition cannot change without re-typesetting the page. Reported as two named key groups so a cell never averages them.
- **PDF font and ICC internals (limit #14):** embedded font programs keep `name`/`OS/2`/`head` (foundry, copyright, build date — measured `head.created` intact on a scrubbed LibreOffice document) and ICC profiles keep their descriptive tags. Header fields are already zeroed by `standards/icc.py`; the tag data is not, because rewriting it changes colour rendering.
- **PDF producer channels, measured (E-PDF, five producers, one document):** at `raw` all three channels identify the producer; after F1 the **serializer channel is closed outright** (header, binary comment, xref kind, object streams, trailer keys, indirect `/Length` — none of them separate producers any more) while the **layout channel is untouched** (operators, number precision, font subsets, glyph digest, stream count) and **size** still leaks. So A2@F1 fails on the layout engine alone, which is what F2 is scoped from. Per W5, only part of that is normalisable without re-typesetting: `struct:glyph_digest` is the predicted floor, and a test asserts it is leaking today so an F2 that passes by breaking the measurement cannot slip through.
- **Our own PDF canonical form:** every output is `%PDF-1.7` with no binary header comment, no `/ID`, catalog as object 1, sorted dictionary keys and one classic xref table. PDF's mandatory skeleton is interleaved through the whole file rather than being a short prologue, so `mandatory_constants()` declares **the empty document our writer emits**, generated not transcribed — a run common to every output that is a substring of a document with *no content* is structure by construction. The declaration is broad, so it is checked rather than trusted: the skeleton must contain no producer string, no timestamp and no padding run. Limit #9 again — it marks a file as canonically rewritten, never as rewritten from what.
- **PDF F2, measured (E-PDF, same five producers):** F2 rewrites every content stream through one writer — number spelling, `Td`/`TD`/`T*` folded into the absolute `Tm` they amount to, show runs merged into one `TJ`, one compression filter, canonical font subset tags, one content stream per page. That **closes the text machine's spelling**: four of the five producers come out with an identical text-operator vocabulary, and the two synthetics that differed only in how they wrote the same page become indistinguishable on it. **A2@F2 still fails**, and what survives is substance rather than style: glyph positions and advances, which font the engine chose, how many objects it embeds, its graphics-operator vocabulary, and file size. Named per key rather than as "the layout channel", because the channel verdict alone would read the same whether F2 had collapsed most of it or none of it.
- **PDF glyph geometry is the F2 floor:** where each glyph sits, how far it advances, where lines break, and which glyphs are in the subset. None of it can change without re-typesetting the page, which would change what the reader sees. Same species as PRNU: document it, do not pretend it is a bug awaiting a fix. F3 (rasterise) moves it into pixel space rather than removing it.
- **PDF character spacing is content, not spelling:** one peer producer (macOS Quartz) genuinely sets `Tc`, so its text-operator vocabulary still differs after F2. Dropping the operator would make the cell pass and change the rendering, which is the wrong trade — the leak stays and is named.
- **PDF F2 coordinates are quantised to 1E-8 user-space units.** Composing a relative move into an absolute matrix can grow the digit count without bound, so emitted coordinates are rounded there. That is 1.7e-7 of a pixel at 1200 DPI — far below anything that can change a rendered dot, and rendered output is byte-identical across all five producers at 150 DPI — but it is a real value change and F2 is described as lossless to well below a rendered dot rather than as bit-exact in the numbers.
- **PDF filters we deliberately do not normalise:** `/DCTDecode` and `/JPXDecode` are lossy, so re-encoding them would be an F3 operation wearing an F2 label; `/JBIG2Decode` and `/CCITTFaxDecode` are lossless but re-encoding a scanned page to Flate multiplies its size. Filter choice therefore survives on those streams.
- **PDF embedded font programs keep their internal subset name.** F2 reassigns the six-letter tag on `/BaseFont` and `/FontName`, but a CFF `FontFile3` carries its own name index and rewriting that means re-emitting the font. Readers use the PDF dictionary, so rendering is unaffected — the original tag survives inside the font program.
- **Our PDF deflate level is 6, and that is measured rather than picked.** The zlib header gives the level away (`78 9C` = 6, `78 DA` = 9). Level 9 was the first choice, copied from PNG F2, and the fingerprint guard failed immediately with ` >>\nstream\nx\xda` as our signature: across the peer corpus four of five producers emit level 6 and one emits level 1, and **none** emits 9 — so level 9 did not normalise our output, it labelled it. Level 6 joins the largest crowd that actually exists.
- **PDF F3 destroys the text layer, and that is the tier's real cost.** Rasterising preserves what the reader *sees* — the page is a picture of itself — but a scrubbed file can no longer be searched, selected, copied from, or read by a screen reader. That is an accessibility regression, not a compression artefact, and it is stated before the tier is offered rather than after it is used. F3 also rounds page dimensions up to the render pixel grid (at most 0.48 pt at 150 DPI).
- **PDF F3 does NOT defeat A2, measured (E-PDF-RASTER).** Structurally F3 passes almost trivially — the file is entirely our own output — and publishing *that* as the verdict would have been the overclaim this project exists to avoid. Attacking the **rendered pixels** instead: a leave-one-document-out nearest-neighbour classifier over ink geometry identifies the producer on **100% of pages (n=30, five producers, chance 0.20, p<0.0001)** after F3, against a valid control of 100% on unscrubbed pages. The typesetter's geometry is painted into the image; rasterising relocates the residual, it does not remove it.
- **The DPI knob is not a Pareto trade, and the reason corrected our own prediction.** The plan expected lower resolution might blur the signal, on the assumption it lived in *sub-pixel* glyph placement. It does not. Swept from 300 DPI down to **18 DPI — where the body text is unreadable — the classifier stays at 100%**. An ablation says why: the **ink-density scalar alone sits at chance** (0.17), so the attack is not reading page size or darkness, while the **column profile alone reaches 100%** — left margin, right edge and horizontal extent of the text block. That is coarse-scale layout geometry, which downsampling leaves entirely intact. Holding page size constant (Letter-only producers) changes nothing. There is no resolution at which the document is still useful and the typesetter is anonymous.
- **Redaction is not metadata scrubbing, and we do not do it.** Text hidden under a black rectangle is a drawing operation with the words still underneath; every tier preserves content, so the scrub preserves the hidden text exactly as faithfully as the visible text — a test asserts this stays true. The tool **warns and never fixes**: it reports invisible text (rendering mode 3/7), text outside the crop box, and text drawn under an opaque fill that covers it. The warning is advisory and never fails the scrub. It deliberately **under-reports**: "text under an opaque fill" in full generality needs blend modes, transparency groups and z-order — a small renderer — so a rotated fill, a fill in a different stream, or any page using a named graphics state is not reported. An empty warning list means "none of these three patterns", never "safely redacted".
- **PDF F2 makes files bigger, and size is itself a leak channel.** Measured on a real 10-page Chrome-printed report: 448 KB in, 452 KB at F1, **590 KB at F2** (+32%), 3.9 MB at F3. F2 grows because every stream is decompressed and re-deflated with no predictor, and because absolute `Tm` positioning is more verbose than the relative `Td` chain a producer emits. `struct:size` is a channel we already report as leaking, so this is a real cost rather than a cosmetic one.
- **Scrubber-fingerprint guard:** confirms our *own* tool leaves no producer/creator string, no odd padding, deterministic ordering, and no modification-time stamping.
- **DOCX package conventions, measured across five producers (E-DOCX-ZIP):** create-system byte, `version made by`, general-purpose flags, extra fields, external attributes, entry order and the timestamp *scheme* all separate producers before a single tag is read. Word writes the ZIP epoch `1980-01-01`, LibreOffice and macOS `textutil` write local wall clock. **Word's deflate is not zlib** — no level reproduces any of its entries, and it declares `super-fast` in flag bits nothing else sets — so matching Word's compressed bytes is not achievable in any language; our writer joins the zlib crowd at **level 6**, which is where LibreOffice, textutil and MAT2 all sit. Compression level is *recovered* by recompression rather than read, because ZIP stores raw deflate with no zlib header byte, and the honest unit is an equivalence class per entry intersected across the package — a first-match search reported three different levels inside one producer.
- **Our own DOCX canonical form:** every output has `[Content_Types].xml` first then parts sorted, `create_system` 0, versions 20, flag word 0, the 1980 timestamp, deflate level 6, `external_attr` 0, and no extra fields, archive comment or directory entries. Limit #9 again — it marks a file as canonically repackaged, never as repackaged from what. The stdlib could not produce it: CPython overrides `external_attr = 0`, the one value Word, LibreOffice and textutil all write, putting the operator's umask in every entry.
- **The DOCX session-ID family (E-DOCX-LOCI, and the E-SESSION-ID target):** `w:rsid*` attributes, the `w:rsids` pool, a standalone `<w:rsid>` inside every `w:style`, `w14:paraId`/`w14:textId` per paragraph, and `w14:docId`/`w15:docId` per document. MAT2 0.14.0 clears the RSIDs and **leaves the rest**, which contradicts the inherited claim that RSIDs survive every scrubber — measured on our corpus rather than repeated from the literature, and not published as a result until E-SESSION-ID runs it with controls. `w14:paraId` is the sharpest of them: it travels with a paragraph pasted into another document, so it links *files to each other*, an attack the A1/A2/A3 ladder does not model.
- **DOCX residuals F1 knowingly leaves:** bookmark names other than `_GoBack` (link targets — limit #20), external relationship targets (removing one breaks a visible link), `word/fontTable.xml` (a weak machine-profile hint), and the versioned namespace declarations that date the producing Word (limit #21). All reported by `residuals()`, never silently dropped.
- **The inherited RSID claim is false, measured (E-SESSION-ID):** MAT2 0.14.0 clears `w:rsid*`, the `w:rsids` pool and the per-style `<w:rsid>`; it **leaves** `w14:paraId`/`w14:textId` (one per paragraph, and they travel with a pasted paragraph, so they link files to each other rather than a file to a producer) and `w14:docId`/`w15:docId` (a persistent per-document GUID, in two namespaces). Our F1 clears all six, on a synthetic corpus and on a real Word document. **ExifTool cannot write DOCX at all** (`Can't write DOCX files`) — a capability gap, reported separately from a failure, because a tool that declines leaves the file untouched while a tool that writes a still-dirty output has misinformed its user.
- **DOCX producer channels, split in two (E-DOCX, four producers, one document):** the **packager** (create-system, external attributes, flag bits, entry-ordering policy, timestamp scheme) and the **document model** (XML declaration spelling, self-closing style, namespace set, part set, style ids, settings keys, `sectPr` defaults, paragraph idiom). At `raw` both channels plus size identify the producer; after **F1 the packager channel is closed outright** while the model channel is untouched, because F1 edits the XML only by deletion. That scopes F2 to one channel from a measurement rather than a guess — and splits it further: `xml_decl`/`selfclose_style` are spelling and should collapse, while `entry_set`/`style_ids`/`paragraph_idiom` are substance and are the candidate floor.
- **Three DOCX A2 features were measuring the wrong thing and were corrected before publication:** the recovered deflate *level class* reported **part size** (it narrows as a part grows, so tiny parts matched levels 5-9 and larger ones matched only 6, though all were written at 6); the raw *entry order* stopped measuring ordering once our writer sorted, becoming a function of which parts exist; and *entry set* was filed under the packager when it is the document program's decision. Without the fixes the published cell would have claimed a packager leak on the strength of a size artifact and a misfiled key.
- **`docProps/thumbnail.jpeg` is dropped whole, not cleaned in place:** it is a rendered page image carrying its own EXIF, it can be **stale** (showing content the document no longer displays — the DOCX relative of PDF revision history), and being a rendering it carries the typesetter's geometry in pixel space, the residual E-PDF-RASTER measured at 100% producer identification. MAT2 strips its EXIF and keeps the picture.
- **DOCX F2 closes spelling and not substance (E-DOCX, four producers, one document):** canonical re-serialisation through one writer closes `xml_decl`, `selfclose_style` and `namespaces` — and the last of those closes limit #21, since an unused versioned-namespace declaration is dropped along with its `mc:Ignorable` entry once F1 has removed the last user. What survives is `entry_set`, `style_ids`, `settings_keys`, `paragraph_idiom`, `sectpr`, `part_types` and `has_theme`: which parts a producer emits, which styles it defines, what it records in `settings.xml`, how it builds a paragraph. None of it can change without changing what the reader sees. Reported per key rather than as a channel verdict, because a channel verdict alone would read the same whether F2 had collapsed most of it or none of it.
- **DOCX F2's canonicaliser had to preserve default namespaces**, and the reason is worth recording: rewriting `<Types xmlns="…">` as `<ct:Types xmlns:ct="…">` is namespace-equivalent XML that **every real OPC reader rejects** — LibreOffice refused all five producers' output. Caught only because the acceptance test is *does it still open*, not *did we write a file*. Whether a part uses a default namespace is decided by the part type, not the producer, so preserving it preserves no fingerprint.
- **Our own DOCX canonical form (F2):** the `mandatory_constants()` declaration includes **our own output for a document with no content**, generated rather than transcribed, because the guard failed the moment F2 landed and reported the complete `_rels/.rels` entry as our signature. That is real convergence rather than a corpus artefact — every package's root relationships part declares exactly one relationship once `docProps/*` is dropped, so canonicalisation gives them all the same bytes. Limit #9 again: it marks a file as canonically rewritten, never as rewritten from what. A test asserts the declared skeleton carries no locus at all, so the broad declaration cannot hide a real leak.
- **DOCX content preservation is checked in pixel space, not only against our own invariant:** each document is rendered through LibreOffice before and after F2 and the images compared. All four real producers render byte-identically. The text-only check was additionally found to be *unsound* on F2 output — a regex extractor treats a canonical `<w:t/>` as an opening tag and swallows the markup up to the next run — so the oracle now parses instead of matching.
- **DOCX F3 collapses the model channel to one key (E-DOCX at F3):** a re-typeset through one engine regenerates the document model rather than relocating it, so `entry_set`, `settings_keys`, `paragraph_idiom`, `sectpr`, `part_types` and `has_theme` all stop separating producers. What survives is `style_ids`, and it is a **primary-production trace** — the engine preserves the *source's* styles rather than rebuilding them from nothing — the same species as M4A's primary-encoding trace. This is the one tier in the project where F3 buys what F2 could not, and the reason is structural: PDF F3 photographs the typesetter's geometry into pixels (E-PDF-RASTER: 100% producer identification), while a DOCX round-trip rebuilds the symbolic model.
- **DOCX F3's rendering cost cannot be measured with the tools on hand, and is reported as unmeasured rather than zero.** Rendering before and after through LibreOffice returns identical images — but LibreOffice is also the engine that performed the round-trip, so the check is the engine grading its own homework. The real cost appears on opening a re-typeset Word document *in Word*, which cannot be scripted on any platform (the same wall the DOCX peer set hits). A test asserts the identical hashes precisely so they are not mistaken for evidence of losslessness.
- **Idempotence, measured across every format:** `scrub(scrub(x)) == scrub(x)` byte for byte at **every F1 and F2 tier** (JPEG, PNG, PDF, DOCX, MP3, FLAC, M4A). That is the strongest available statement that a canonical form really is canonical — a second pass finding anything to change would mean the first left an input-dependent trace, which is what the A2 defense claims it does not do. **F3 is deliberately not a fixed point** on any format, because a lossy re-encode run twice is a second generation; asserted rather than left as folklore, so nobody later "fixes" it (limit #29).
- **HEIC is an item table, not an image in a box, and that is the whole difficulty.** The picture is a grid of 61–95 HEVC tiles; the metadata items, a thumbnail and 6 auxiliary images sit beside it in the same `mdat`, all addressed by **absolute offset** from one `iloc` table. Removing a metadata item therefore relocates everything after it — the `stco`/`co64` trap M4A taught, in its second guise. Two measurements made the rebuild tractable: `mdat` is **100% covered by item extents** (zero gaps, on every synthetic and real file), so the new `mdat` is exactly the kept items concatenated; and `iloc` field widths are fixed per file, so rewriting offsets does not change the box's size and layout and offsets never chase each other. The acceptance test **decodes** the image through an independent HEIF decoder rather than merely walking it, because M4A's failure mode is a file that parses perfectly and decodes to garbage.
- **A tiled auxiliary image is not the eight bytes that describe it, and removing only those bytes removed nothing.** On an iPhone the depth maps, mattes and gain map are usually **grids**: `iloc` points at an 8-byte grid descriptor and the picture itself lives in twelve or thirty separate `hvc1` items. The first version of this handler dropped the item named in `iinf` and left every tile in `mdat` — **381 KB of a 1.17 MB photo, 707 KB of a 1.78 MB one**, on all six real files — with nothing left naming them, so every tag-based check (ours and ExifTool's) reported the file clean. Removal is now computed on the `dimg` graph: an item survives only if a surviving image still composes it, and removed items are barriers so nothing is reached through them. The check that catches it is **connectivity, not naming**, and deliberately undirected — deleting a tiled image also deletes the reference that made its tiles tiles, so a directed walk reads the abandoned tiles as top-level items and calls the file clean.
- **`iloc` was writing offset 0 for every item stored in `idat`**, because the model recorded those offsets as -1 (to keep anything that moves bytes away from them) and the writer clamped the -1 away. The primary grid survived it — it is written first, so 0 was its real offset — and everything beside it read the primary's descriptor instead of its own. It is the `stco` trap one level below `mdat`, and the channel it corrupts is one the pixel oracle cannot see, so six pixel-identical tests stayed green over it. `idat` is now re-packed like `mdat`, which also stops the *descriptions* of removed auxiliary grids being copied into the output.
- **`grpl` is a fourth table that names items by id** and was copied through verbatim, so an entity group could outlive the item it names. Rebuilt with the rest now — the same class of dangling reference as `iref`, in the box nobody looks at.
- **HEIC item properties are shared by index, so pruning them means renumbering.** Keeping `ipco` whole left a scrubbed iPhone photo still advertising `AuxiliaryImageType: urn:com:apple:photo:2019:aux:semanticskinmatte` after the matte itself was removed — the file no longer carried Apple's person-segmentation output but still announced that the segmentation had run, which weakly implies what it found. Caught by ExifTool on a real photo, which is exactly why the scrub report cross-checks with a second implementation.
- **HEIC colour profiles keep their copyright, and that is limit #14 in a third format.** The ICC *header* (device manufacturer, creator, build date) is zeroed by `standards/icc.sanitize()`; the tag data is the colour transform and is not touched, because rewriting it would change the picture. So `Copyright Apple Inc.` survives inside the profile — narrowing to the platform, not the person — and the cross-check is told to expect it there rather than reporting a documented residual as a scrub failure.
- **PDF F1 size, measured (a one-page pdfTeX CV):** 44,620 → 49,344 bytes, **+10.6%**, against **+0.0% / +0.5% / +0.6%** on three PDFs that carry no `/ObjStm`. The delta is object-stream unpacking, not the rewrite as such: our serializer emits every object individually, and object-stream *use* is one of the serializer-channel features E-PDF measured as closed at F1 — so re-packing to match the input would reopen the channel we closed. Size is already published as a surviving A2 feature at every PDF tier (`struct:size`), and this is the F1 half of it, previously recorded only for F2 (limit #18). Found by scrubbing a real user file rather than by a test.
- **The ISOBMFF `mdat` largesize trap, and the check that now stands in for a decoder:** a writer may use the 64-bit `mdat` header (`size == 1`, then a 64-bit length) for a box that fits in 32 bits, and **AVFoundation does** — a 17 KB `mdat` with a 16-byte header. M4A F1 reconstructed that header as 8 bytes when measuring the input rather than reading `header_len` from the parse, so the predicted "before" and "after" agreed, the delta came out **0**, `shift_chunk_offsets()` was never called, and the output carried byte-identical media with every `stco` entry 8 bytes wrong. It parsed, reported the right duration, and decoded to noise. Shipped from Phase 2 until MP4 M3 decoded an Apple-muxed file. Two guards now: the input offset is read, never reconstructed (`mdat_payload_offset_of_input`), and `strip_and_repack` follows **every chunk offset from input to output and compares the bytes it lands on**, refusing rather than emitting a mismatch. The bug is pinned by a hand-built largesize fixture that needs neither ffmpeg nor a Mac.
- **The ISOBMFF `hdlr` name is a producer channel that no tag-oriented tool touches:** ffmpeg writes `VideoHandler`/`SoundHandler`, AVFoundation writes `Core Media Video`/`Core Media Audio`. It is not a tag, so `exiftool -all=` leaves it and reports the file unchanged; our own M4A F1 left it too until MP4's M0 went looking. Now blanked by the shared strip for M4A and MP4 alike — written once in `standards/isobmff.py` rather than per format, which is the point: the leak existed in M4A precisely because the engine had been written for one format.
- **Blanking it introduces a constant, and the fingerprint guard was right to say so.** Every output then carries a byte-identical `hdlr` box, since the rest of the box is the format's. Declared as a mandatory constant, **generated from the same `blank_handler_name()` the strip calls** so it cannot drift, and bounded by a test asserting the declaration carries no locus — the DOCX empty-`_rels` pattern. Getting there needed two corpus fixes rather than a wider declaration: the M4A diverse corpus varied sample rate and layout but not **language** (the field immediately before `hdlr`) or **duration** (which sets the size of `minf`, immediately after), so the guard reported one maximal run welding our constant to its unvarying neighbours and no declaration of the box alone could cover it. DOCX M11's lesson repeated exactly: when the guard reports something too broad, suspect the corpus before widening the declaration.
- **The A2 plugin never measured `hdlr` names, so the leak was invisible to the matrix too.** Regenerating M4A's matrix after the fix changed **no verdict and no leaking feature** — the channel was not in the feature set. A locus absent from both the scrubber and the measurement is exactly what the DOCX locus census exists to prevent, and it argues for adding handler names to the ISOBMFF structural features when MP4's plugin lands at M4.
- **MP4 producer channels, split two ways and measured (E-MP4, four producers, one picture):** the **muxer** (brand, compatible-brand list, top-level box order, `moov` position, `free` slack, `hdlr` names, `mdat` header width, timestamp scheme) and the **video encoder**, which reaches the categorical channel only through `struct:size`. At `raw` all nine muxer features plus size separate the producers. After **F1 five close** — `free_bytes`, `box_inventory`, `handler_names`, `mdat_header_form`, `timestamps_present` — and four survive: `brand`, `compatible_brands`, `top_level_order`, `moov_before_mdat`. Reported per key rather than as a channel verdict, because a channel verdict reads the same whether a tier collapsed most of it or none of it. The four survivors are the F2 specification. **Re-measured on merging** (2026-10-04), against the F1 that rebuilds `mdat` instead of copying it: the same five close and the same four survive. A tenth feature, `track_ids` (the surviving IDs and `next_track_ID`), was added then and separates **no one** in this peer set, raw or scrubbed, because none of the four producers writes a timed-metadata track; on a QuickTime clip F1 leaves `next_track_ID` one past the tracks it dropped (limit #37), which goes into the F2 specification rather than being patched blind.
- **The MP4 peer set includes a second muxer implementation, not just a second invocation:** `avfoundation` is a pass-through re-mux through Apple's muxer, so the coded video is identical and only the container differs. macOS-only, and its absence is stated in the cell rather than silently shrinking the peer set to three ffmpeg configurations — measuring a container channel against one implementation's options would mostly measure the options.
- **`handler_names` and `mdat_header_form` are in the feature set because Phase 4 found them and nothing else was looking.** The first is the field `exiftool -all=` leaves while reporting a file unchanged; the second is the largesize header that caused limit #41. A fingerprint feature a scrubber normalises by construction is still worth measuring: it is the difference between "we handle this" and "we believe we handle this", and a future change that stops closing it fails a cell instead of passing quietly.
- **The MP4 fingerprint-guard corpus had to vary the TRACK SHAPE, not just the container.** The first version varied brand, layout, largesize form and track count while every hand-built track kept the same duration, dimensions and timescale — so all four outputs shared a byte-identical **389-byte `trak` box** and the guard reported the whole thing as our signature. It was right: an undiverse corpus cannot distinguish a constant the tool introduces from one the corpus never varied. Third time this project has hit it (DOCX M11, M4A at M3, here), and the fix is the same each time — vary the thing, do not widen the declaration. **A fourth, on merging:** the fixture gained the sample tables and data reference the rebuild needs, every scrubbed `minf` landed in 0x100–0x1ff, and the high bytes of its size word were common to all four outputs; one shape now carries ninety samples instead of one.
- **The MP4 A2 channel set is platform-dependent, and the verdict is not.** With the macOS-only AVFoundation producer the peer set separates on nine structural features; with ffmpeg configurations alone it separates on three, because ffmpeg writes one set of `hdlr` names, one brand and one `mdat` header width whatever the flags. **A2@F1 fails either way** — measured by re-running the experiment with the producer removed, not assumed — so no published verdict depends on a Mac. A test contrasts the two peer sets directly and asserts the ffmpeg-only one genuinely cannot see `handler_names`, so limit #44 cannot quietly become false. `swiftc` is recorded in the CI contract's optional list with that reasoning rather than left to be discovered.
- **Camera RAW identity removal (M16, not yet a shipped format):** on five real files the serials, owner names and counters are blanked in place or, where measured decode-irrelevant (Sony, Apple), the whole maker note is removed -- sensor data bit-identical and the camera-white-balance render pixel-identical on all five. **ExifTool is not a sufficient check here:** after blanking every field it names, the Canon 80D still carried its owner's name inside `CameraInfo`, a model-specific binary block ExifTool does not decode for that body. Removed by searching the maker note for every blanked text value; per-model layouts are not modelled. Two residuals are stated rather than measured yet: a blanked field keeps its length (a run of zeros where every camera writes text), and Nikon's colour block stays enciphered under the original serial and shutter count.
- **Camera RAW F1 (M17):** removes dates in whichever directory a maker put them (Nikon in IFD0, Sony repeated in IFD1), the GPS directory whole, software and XMP, the dates and time zones inside maker notes (Canon's time-zone city, Nikon's power-up time, Olympus's UTC date), a DNG's original file name, embedded original raw and Adobe private block, and a DNG 1.6 semantic mask (the HEIC matte decision, #31). Tag `0xC634` is removed only in a DNG: in a Sony ARW the same tag points at the enciphered white balance the decoder needs.
- **RAW previews are kept, cleaned, by measurement:** the iPhone DNG's 5.4 MB preview carries its own EXIF with the GPS, a colour profile and a 171 KB trailing image. It goes through the JPEG F1 keep-list with its **colour profile kept** (dropping a Display P3 profile would recolour every viewer showing the preview) and is padded back to its own length. macOS QuickLook's thumbnail of the cleaned file is **pixel-identical** to the original's, so keeping previews costs a viewer nothing. The other four previews carry no metadata and are untouched.
- **Canon CR3 (M18):** the MP4 container around a still photo. Its metadata is four little TIFF files inside Canon's own box, cleaned block by block with the same tables, and a timed-metadata track (`CTMD`) whose sample carries a timestamp and the shot count **beside the white balance LibRaw reads**: zeroed whole, the camera white balance became `[0, 1, 0, 0]` and the picture lost its colour, so it is edited record by record. The XMP packet is rewritten empty, padded to its length as XMP itself provides. Everything is edited in place, because a table in Canon's box records absolute positions.
- **Canon `CameraInfo` is blanked whole:** a model-specific block that held a copy of the owner's name on the 80D and the shot count on the R6 Mark III, at offsets that differ per body. LibRaw's sensor data, camera white balance and render are identical without it on both bodies; **other Canon bodies are not measured.**
- **Fujifilm RAF (M18):** every identity value is in the preview JPEG's own EXIF, Fujifilm's maker note included — and that EXIF **cannot be dropped**: stripped, LibRaw no longer decodes the file (the same failure the survey saw from `exiftool -all=`). It is cleaned in place instead. Then a search of the bytes found the body serial and a date **again**, inside the Fuji header block, which ExifTool does not decode; every removed text value is searched for there and blanked. The third copy of this kind in Phase 4 (after the iPhone video's stale GPS and Canon's `CameraInfo`): the measuring stick reads fields, so the residual check reads bytes.

E-ENGINE and E-PDF-RASTER assert their own controls: if the classifier cannot
identify the producer on untouched files, the result on scrubbed files is reported as
**inconclusive** rather than as a pass. A test that cannot detect the thing it is
looking for proves nothing. E-PDF-RASTER additionally **ablates** its own feature
vector, because a classifier at 100% shows the producer is identifiable without
showing what from — and "glyph geometry survives" would have been an interpretation
laid over a number that could equally have come from page size.
