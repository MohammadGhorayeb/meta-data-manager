A tool that **irreversibly strips metadata from files of arbitrary type**, for privacy and anonymization. "Irreversible" means *forensic unrecoverability from the scrubbed file itself* — not merely deleting visible fields — against a medium-tier adversary (a journalist or amateur investigator using off-the-shelf forensic tools).

## Status
Phase 0 (harness + spine), **Phase 1 images complete** (JPEG F1/F2/F3, PNG F1/F2), and **Phase 2 audio complete** — MP3 (F1 + F3, cross-engine A2 evidence), FLAC (F1 + F2, lossless A2) and M4A (F1/F2/F3, the format MAT2 refuses). **Phase 3 documents is complete**, and **Phase 4 is under way: HEIC** — every iPhone photo — is closed at F1, measured and plugged into the harness, and **video (MP4 and MOV) works at F1**: every iPhone video, including a stale second copy of its GPS that ExifTool leaves in place and MAT2 cannot open. Its matrix is published, so it is in the badge above on the same terms as every other format: a claim with a measurement behind it, enforced by a test. **Camera RAW works at F1** for every format surveyed — Canon (CR2 and CR3), Nikon, Sony, Fujifilm, Olympus, Panasonic and iPhone ProRAW: serials, owners, dates, GPS and the previews' own metadata removed without moving a byte, with the sensor data and the camera-colour rendering unchanged; its harness matrix is published. **PDF is complete across all three tiers** — our own walker, serializer, content tokenizer, content-stream canonicaliser and rasteriser, recursive into embedded images, plus a redaction-risk advisory — and the revision-history, producer-channel and pixel-space experiments are all measured (see below). **DOCX is complete at F1, F2 and F3** on the same footing: our own ZIP reader and writer, an OPC relationship graph, byte-level XML surgery that deletes without rewriting, a canonical XML re-serialiser, and recursion into embedded images. Its A2 result is measured per producer channel, with content preservation verified by rendering the document before and after. Fully implemented and measured, **901 tests** — the number is checked against what pytest actually collects, because a hand-maintained count is a published claim with nothing behind it. Per-format Pareto matrices are generated under `tests/harness/results/`, and the scrubber-fingerprint guard passes. University implementation project; a working tool is the deliverable. A plain-language progress report is at [`docs/client_report.pdf`](docs/client_report.pdf) (itself scrubbed at F2 by this tool — same pixels, no Skia signature, no timestamp); a benchmark vs standard tools is at [`docs/benchmark.md`](docs/benchmark.md).

A1 (metadata) is defeated everywhere it has been measured. A2 (encoder fingerprint) is defeated by re-encoding — and **twice now at no quality cost at all**: **PNG F2** and **FLAC F2** are lossless, returning bit-identical pixels and bit-identical audio, while **JPEG F3** and **MP3 F3** must spend a lossy generation to get there. The dividing line is whether the fingerprint lives in a separable layer (PNG's deflate, FLAC's metadata blocks and framing) or is baked into the compressed content itself (JPEG's DQT, MP3's LAME/Xing contour). Each format's fingerprint and residuals (PRNU, primary quantization, MP3 generation loss, within-class anonymity) are documented, never silently claimed clean.

\* **M4A carries two producers in one file** — the muxer that arranged the boxes and the encoder that made the coded audio — and the cells say which one leaked rather than averaging them. F2 fully normalizes the muxer layout (box order, brand, `free` slack) while copying the audio stream, so it is lossless. F3 additionally collapses producers whose first-generation audio was identical to **byte-identical output**; what survives is the *primary-encoding trace* left by a source that was itself encoded differently (192 kbps vs 128) — and it is now narrowed to a single channel, **file size** (~1.4%), since the audio itself no longer betrays it. That trace has since been measured (**E-M4A-AUDIO**): the source's own quality setting reads at **0.88** on untouched and copy-tier files and **falls to chance (0.50) after F3**. Engine identity was *not* separable even on untouched files (0.56) — ffmpeg's AAC and Apple's are near-twins spectrally — so that question is reported as unanswerable with this corpus rather than claimed either way. **MAT2 refuses M4A entirely** (measured, 0.14.0), so every cell here is capability the benchmark alternative lacks.

\*\* **PDF also carries two producers** — the *serializer* that laid out the bytes and the *layout engine* that typeset the page — so its A2 cells name which one leaked instead of averaging them. Measured across five producers rendering one document (Chrome/Skia, LibreOffice, macOS Quartz, and two pikepdf synthetics that differ in both serializer and layout style): at `raw` all three channels identify the producer; after **F1 the serializer channel is closed outright** — header, binary comment, xref kind, object streams, trailer keys and indirect `/Length` no longer separate anyone — while the layout channel is untouched, because F1 never rewrites a content stream. **F2 rewrites every content stream through one writer** (numbers, `Td`/`TD`/`T*` folded into the absolute `Tm`, show runs merged into one `TJ`, one filter, canonical subset tags, one stream per page) and that **closes the text machine's spelling**: four of the five producers come out with an identical text-operator vocabulary, and the two synthetics that differed only in *how* they wrote the same page become indistinguishable on it. A2@F2 still fails, and what survives is substance rather than style — **glyph geometry** (where each glyph sits, where lines break, which glyphs are in the subset), which font the engine chose, how many objects it embeds, and file size. Glyph geometry cannot change without re-typesetting the page, so it is the F2 floor by the same logic as PRNU, and F3 will move it into pixel space rather than remove it. Content preservation is checked in pixel space, not just against our own invariant: all five producers render **byte-identical PNGs at 150 DPI** before and after F2. **F3 rasterises** — every page rendered by one poppler build at one resolution, rebuilt around the images — and *structurally* it passes almost trivially, since the file is then entirely our own output. Publishing that as the verdict would have been an overclaim, so the A2@F3 cell is decided by attacking the **rendered pixels** instead (**E-PDF-RASTER**), and it **fails**: a leave-one-document-out nearest-neighbour classifier over ink geometry names the producer on **100% of pages** (n=30, five producers, chance 0.20, p<0.0001), against a valid 100% control on unscrubbed pages. **The DPI knob is not a Pareto trade**, and measuring corrected our own prediction: we expected coarser rendering to blur a *sub-pixel* signal, but swept from 300 DPI down to **18 DPI — where the body text is unreadable — the classifier stays at 100%**. An ablation says why: **ink density alone sits at chance** (0.17, so it is not reading page size or darkness) while the **column profile alone reaches 100%** — margins and text extent, which is coarse layout geometry that downsampling cannot touch. So the glyph-geometry residual is confirmed as the PRNU species: rasterising relocates it, it does not remove it.

\*\*\* **DOCX carries two producers too** — the **packager** that laid out the ZIP and the **document model** that wrote the WordprocessingML — so its A2 cell names which one leaked rather than averaging them. Measured across four producers rendering one document (LibreOffice, macOS `textutil`, MAT2's own rewriter, and a synthetic writer): at `raw` all three channels identify the producer, and after **F1 the packager channel is closed outright** — create-system, external attributes, flag bits, entry-ordering policy and timestamp scheme no longer separate anyone — while the model channel is untouched, because F1 edits the XML only by deletion. That is the same shape PDF F1 had. **F2 then rewrites every part through one writer** — canonical namespace prefixes with unused declarations dropped, sorted attributes, one self-closing style, one declaration form — and **closes exactly the half that is spelling**: `xml_decl`, `selfclose_style` and `namespaces` stop separating anyone. A2@F2 still fails, and what survives is substance rather than style — which parts a producer emits, which styles it defines, what it records in `settings.xml`, how it builds a paragraph, its section properties. None of that can change without changing what the reader sees. Content preservation is checked in pixel space, not just against our own invariant: all four producers render **byte-identically through LibreOffice** before and after F2. **F3 then re-typesets the document through one engine — and this is the one tier in the project where F3 buys what F2 could not.** The difference from PDF's F3 is structural: rasterising *relocates* the typesetter's geometry into pixels, where a classifier read the producer off the ink on 100% of pages, while a DOCX round-trip **rebuilds the symbolic model**. The model channel collapses from seven keys to **one**, and the honest reading is what that key is rather than that one remains: every producer comes out with the engine's own part set, settings, paragraph idiom and section properties, and what survives is that a document whose *source* defined a style keeps it — a **primary-production trace**, the same species as M4A's primary-encoding trace, describing the document's origin rather than the tool that handed us the file. A2@F3 still fails, and says which key. **The tier's cost is reported as not measured rather than as zero**: rendering before and after through LibreOffice returns identical images, but LibreOffice is also the engine that did the round-trip, so that check is the engine grading its own homework. The real cost appears on opening a re-typeset document in Word, which cannot be scripted on any platform. **Microsoft Word is not in the peer set**, and the cell says so: it has no CLI on any platform, so it cannot render *our* document, and an unrelated Word file would have the classifier separating documents while appearing to separate producers.

\*\*\*\* **HEIC's A2 cell is a measured failure, and that is the point of running it.** F1 is a bit-preserving tier: it relocates items and rebuilds the tables that locate them, and deliberately changes nothing else — so every choice the writing software made passes straight through. Measured across **three container-writer profiles wrapping byte-identical HEVC tiles** (a test checks that claim rather than asserting it), what separates them is `brand`, `compatible_brands`, `meta_table_order`, `iloc_widths` and `size`. Published as a failure with each feature named, because that list **is** the specification for an F2: one canonical brand, one table order, one set of `iloc` field widths, canonical item numbering, tiles untouched. The same method Phase 3 used on PDF — measure which producer channel leaks before designing the fix. F2 and F3 do not exist yet and their cells say `not_tested`, never `fail`: a tier that was never run has no verdict to report.

† **MP4/MOV's A2 cell is a measured failure, with its channel named** — the same shape as HEIC's. Four producers, one of them a genuinely different muxer (AVFoundation, pass-through so the coded video is identical): at `raw` nine muxer features plus size separate them; **F1 closes five** — the padding, which boxes exist, the track handler names, the width of `mdat`'s length field, and whether timestamps were written — and **four survive**: `brand`, `compatible_brands`, `top_level_order`, `moov_before_mdat`. Those four are the specification for an F2, together with renumbering the tracks that remain, since a scrubbed iPhone clip's next-track number still counts the hidden tracks F1 removed ([limit #37](docs/limits.md)). The peer set has no phone in it, and the cell says which producers it had. A1 passes in the harness and, separately, in the format's own tests: a hand-built QuickTime movie carrying every locus measured on real files, each planted value checked absent from the output **bytes**; five real iPhone and Mac clips decoded frame for frame before and after; and a check that **no byte of `mdat` is left that no sample table points at** — the camera writes a stale copy of its GPS into exactly those bytes ([limit #34](docs/limits.md)).

‡ **Camera RAW's A1 cell is measured in the harness** (M19) across all five maker-note layouts, on fixtures whose planted metadata differs only in content, with content identity decoded by LibRaw rather than parsed. **A2 is stated, not run:** make, model and lens model are kept on purpose (the decoder chooses the colour profile by them), so the model survives by design, and whether a cleaned file still points to one camera *body* needs several files from two bodies of one model, which the corpus does not have. Beyond the harness, on eight real files (Canon CR2 and CR3, Nikon NEF, Sony ARW, Fujifilm RAF, Olympus ORF, Panasonic RW2, iPhone DNG) every serial, owner, counter, date, time zone and GPS value ExifTool finds before is gone after, no original text value is left in the bytes, LibRaw's sensor data is bit-identical and a render with the camera's own white balance is pixel-identical; CI runs the same checks on a hand-built DNG in every maker-note layout. The scrubber-fingerprint guard passes with three declared marks, each the unavoidable trace of cleaning in place: zeros where a value was, and a cleaned preview's start and end ([limit #47](docs/limits.md)).

MP3 A2 is now measured **across encoder engines**, not just front-ends: the peer set includes [shine](https://github.com/toots/shine), a fixed-point encoder that is not libmp3lame and writes no Xing/LAME header at all. Two experiments back the A2@F3 cell — **E-LAME** in header space (all producers collapse to one canonical signature) and **E-ENGINE** in audio space, which asks the harder question the headers can't: with the header normalized, can a peer-corpus adversary still recover the source *engine* from the waveform?

The claim is deliberately **per sample-rate group**, and is verified in each group rather than in aggregate. 192 kbps CBR is illegal for MPEG-2 sample rates, so those files emit at 160 and form their own group; the group follows the source's sample rate, which is content we **preserve by design** — resampling would change the audio. Producer-anonymity holds inside every group, in structure (both rates pass E-LAME) and in sound (E-ENGINE: 44.1 kHz **0.89 → 0.53**, 22.05 kHz **0.94 → 0.58**, against chance 0.50; neither significantly above chance at n=36). Scope stated honestly: spectral features; MDCT-domain classifiers untested. Every known limit lives in [`docs/limits.md`](docs/limits.md).

### Phase 3 — documents (complete)

PDF and DOCX at all three tiers. The plan and every experiment are in [`docs/p3_documents_plan.md`](docs/p3_documents_plan.md). The two named targets were PDF **incremental-update history** (old revisions left in the file: the famous redaction-disclosure mode) and **OOXML RSIDs** — the second of which turned out to be already solved upstream (M12).

**Measured (M1).** A PDF is edited by *appending*, so "deleted" text is still in the file; truncate at an earlier `%%EOF` and the earlier draft opens as a document. On a 3-revision corpus: **ExifTool `-all=` adds a fourth revision and removes nothing** (it warns about this itself), while **MAT2** destroys the document's history by re-rendering but then clears `/Info` by appending an update of its own — leaving `cairo 1.18.4` and a **wall-clock timestamp with the operator's UTC offset** one revision down, reproduced on both its paths and on a real 295 KB file. Details in [`docs/benchmark.md`](docs/benchmark.md) Evidence 6.

**Built (M2): PDF F1.** A rewrite from the object graph through **our own serializer** — pikepdf reads, we emit the bytes, because qpdf's constant header comment and its inherited `/ID[0]` both fail this project's own fingerprint guard. History dies by construction: only what the catalog reaches is written, so superseded objects are never emitted and there is no deletion pass to get wrong. Recursive from day one — an embedded JPEG goes through the Phase 1 handler and its entropy-coded scan comes back byte-identical while its EXIF and thumbnail are gone. Clears `/Info`, XMP *wherever it hangs* (including off an image), `/ID`, page `/Thumb`, `/PieceInfo`, `/SpiderInfo`, OCG `/CreatorInfo`, annotation authors, and **inline images** — a `BI … ID … EI` JPEG that no object-graph walk can see. Verified on six real producers (Skia, LibreOffice, Quartz, cairo, ExifTool output, synthetic), text byte-identical throughout. Encrypted, signed, XFA, attachment-bearing and hybrid-xref files are **refused**, not half-scrubbed.

**Measured (M3): which half still gives you away.** With the metadata gone, the producer is still identifiable — but the experiment says *which* channel, not just *that* it fails, which is the whole reason it runs before F2 is designed. The serializer channel is closed; the layout channel is open; that is F2's scope, and glyph geometry is the predicted floor within it. Details in the footnote above and in [`docs/p3_documents_plan.md`](docs/p3_documents_plan.md) §2.3.

**Built + measured (M5): PDF F3, and the DPI knob that isn't.** Rasterise-and-rebuild — the MAT2/Dangerzone technique, offered rather than assumed, because it costs the document its selectable text (an accessibility regression, stated before the tier is offered). Its residual was then attacked in pixel space rather than asserted away; see the footnote above. Also **W7, the redaction advisory**: PDF warns when a document looks like someone tried to redact it by drawing a black box, because every tier preserves content and therefore preserves the words underneath — a test asserts that the hidden text still comes out of `pdftotext` after a successful scrub, so the warning can never quietly stop being necessary. It warns and never fixes, never fails a scrub, and deliberately under-reports. Details in [`docs/p3_documents_plan.md`](docs/p3_documents_plan.md) §2.5.

**Built + measured (M4): PDF F2, and the honest A2-at-F2 answer.** A content-stream canonicaliser that folds every equivalent spelling into one — and needs no font metrics to do it, because `Td`/`TD`/`T*` are relative to the *line* matrix, which showing text never moves. The text machine's spelling is closed; **glyph geometry is not, and is named as the floor rather than rounded away** to make a cell pass. Three bugs were caught before publication, each of which silently moves text while still painting every glyph: a pending move dropped when a font change interrupted it, leading treated as text-object state when `TL` is graphics state saved by `q`/`Q`, and invoked streams (forms, patterns, Type3 glyphs) assumed to start in the default state when they inherit the caller's. **The fingerprint guard failed the moment F2 landed and was right to** — every stream was being re-encoded at deflate level 9, which no peer producer emits; four of five emit level 6, so we now do too. Details in [`docs/p3_documents_plan.md`](docs/p3_documents_plan.md) §2.4.

Redaction — text under a black box in a single-revision file — is a *different* leak that none of this touches, and is kept explicitly separate ([limit #13](docs/limits.md)).

**Complete: M6–M14 — OOXML/DOCX**, deliberately cut into small steps ([plan](docs/p3_documents_plan.md) §1 W8–W15, §3). The first four deliberately landed *before any scrubbing happened*, because the two things that have actually bitten this project are normalising by guesswork (PDF's deflate level 9, which labelled our output instead of hiding it) and a determinism hole the in-process floor test cannot see.

**Measured (M6): what real producers write into a ZIP, and why we write the container ourselves.** A byte-level census across five producers (Word, LibreOffice, macOS `textutil`, MAT2 output, stdlib `zipfile`), reading the ZIP itself rather than through a library that normalises away exactly the fields being measured. **Compression level had to be *recovered*, not read** — a ZIP stores raw deflate with no zlib header byte — and the first attempt was wrong in an instructive way: first-match search reported three different levels *inside one producer*, because on parts this small levels 4–9 produce identical bytes. The honest unit is an equivalence class per entry intersected across the package, and with that correction all three zlib-based producers collapse to exactly **level 6** — the same answer PDF F2 reached by a completely different technique, now measured twice. **Word's deflate is not zlib at all**: no level reproduces any of its entries, and it declares `super-fast` in flag bits nothing else sets, so "match Word" is not an option in any language. Word also confirms the `1980-01-01` timestamp constant from the other side — it writes the ZIP epoch itself, while LibreOffice and `textutil` write local wall clock, making the timestamp *scheme* a producer channel before any date is read.

The **decision**, settled by measurement as the PDF serializer decision was: **we write the ZIP container ourselves.** Every field pins through stdlib `zipfile` except one — `external_attr`, where CPython does `if not zinfo.external_attr: zinfo.external_attr = 0o600 << 16`, so the single value that joins the crowd (`0`, written by Word, LibreOffice and textutil alike) is the one value the library refuses to keep, and a stdlib-written package carries **the operator's umask in every entry**. Both stdlib traps are now regression tests rather than comments, so a CPython change reports itself instead of quietly moving our output. Details in [`docs/p3_documents_plan.md`](docs/p3_documents_plan.md) §2.7.

**Measured (M7): the list F1 gets written against.** A census of every metadata-bearing locus in a package, each carrying a **disposition** — drop / keep / recurse / refuse — where a locus found with *no* rule comes back `UNCLASSIFIED` and fails a test. A leak cannot hide in a place nobody wrote a rule for, because the census names the place. 35 loci are ruled, and because no real producer writes a tracked change, a comment, a sensitivity label or an embedded image, a synthetic **torture package** carries one instance of every locus the table names, so a test can assert that **no rule fails to fire** — the rule table is tested, not trusted. It caught a bug in itself immediately: `w:name` was ruled as "bookmark names" and fired **386 times in one document**, because WordprocessingML reuses it on fonts, styles and compat settings — a context-free rule would have had F1 deleting font names, a content-preservation failure rather than a leak. The MAT2 column then reproduced the §2.6 probe through an entirely different mechanism: RSIDs cleared, `w14:paraId`/`w14:textId`/`w15:docId`/`w:proofErr` left exactly as Word wrote them. Also worth quoting against "surely `app.xml` is boilerplate": LibreOffice writes `LibreOffice/26.2.4.2$MacOSX_AARCH64` — application, version, OS **and instruction set** in one property. Details in [`docs/p3_documents_plan.md`](docs/p3_documents_plan.md) §2.8.

**Built (M8): the OPC walker, and identification when the magic decides nothing.** Every format so far was decided by its magic prefix; `PK\x03\x04` decides nothing, because XLSX, PPTX, ODT, EPUB, JAR and a plain archive all begin with it — so `claims()` opens the central directory and looks for the parts that make a package a DOCX, and a test builds an XLSX-shaped package to prove it is not claimed. The walker reads from the **central directory**, never by scanning local headers, because a ZIP stores each header twice and which copy a reader trusts is itself an attack surface; disagreements are reported per field rather than silently resolved. Refused with a stated reason: ZIP64, duplicate entry names, traversal paths, encrypted entries, trailing or prepended bytes, CRC mismatches, malformed part XML, signatures, macros and OLE embeddings. **ZIP64 detection was wrong on the first attempt and so was the test that passed it** — the check looked only at the ZIP64 end records while the real hazard hides in an entry's extra field, where 64-bit sizes supersede the header's and being ignored means silently reading a part at the wrong length; the test meanwhile set a field `writestr` overwrites, so it passed vacuously. Both fixed. The safety property F1 depends on is `orphans()`: dropping a part means dropping its relationship *and* its content-type override, or Word shows "unreadable content" and the scrub has destroyed the document while reporting success. The handler was deliberately **left out of dispatch** until F1 landed, so the tool never advertised a format it could not scrub; it is registered now, and registered **last**, because its magic is the weakest of any handler here. Details in [`docs/p3_documents_plan.md`](docs/p3_documents_plan.md) §2.9.

**Built (M9): the ZIP writer, and a determinism hole closed for every format.** The writer is pinned to the constants M6 measured — FAT create-system rather than the Unix one that names the machine we ran on, the `1980-01-01` constant Word itself writes, deflate level 6, `external_attr = 0`, no extra fields, no directory entries — and its entry order is sorted specifically so it can never be inherited from a dict or a set. It is checked by three readers, including Info-ZIP `unzip -t`, because `zipfile` agreeing with us proves only that two Python views of the format agree. **A test here was wrong before the code was**: the level assertion failed against a correct writer because data that repetitive emits identical bytes at levels 6–9 — the level class is a property of the data — so it now runs on varied text where the levels separate and asserts `levels == {6}` exactly. Separately, the harness's five determinism repeats all run in **one interpreter sharing one hash seed**, so a `set` iteration deciding output order is invisible to it and differs on the next CLI run. That check now covers **every (format, fidelity) the tool offers** — in separate interpreters under varied `PYTHONHASHSEED`. Every existing format already passed: the hole was latent, not active, and it is now a guard rather than a hope, in place before the format most likely to trip it. **The list was hand-maintained and went stale, which Phase 4 M4's pre-flight caught:** it still held the original 15 pairs, so DOCX's three tiers and HEIC's one had never been added and MP4's made 20. It is now derived from the dispatcher, with a test asserting every offered tier is either checked or **named in an exclusion list with a written reason** — DOCX F3 is the one exclusion, because its bytes come from LibreOffice rather than from us. DOCX F1/F2, which the stale list had skipped entirely, now pass. Details in [`docs/p3_documents_plan.md`](docs/p3_documents_plan.md) §2.10.

**Built (M10): DOCX F1 — and three leaks that a weaker test would have passed.** F1 means what it means for PDF: we only delete. Parts go whole, attributes and elements are excised in place, every other byte stays where it was, and the text comes out byte-identical — which rules out the obvious implementation, since parsing a part and re-serialising it rewrites namespace declarations, attribute order and tag style. That is canonicalisation and it belongs to F2. Measured on all five producers: text byte-identical, every census locus gone, every output still opens through LibreOffice, `exiftool` reports no identity field. **The test change that mattered:** the session-ID assertion originally checked `b"w:rsid" not in out` against the *archive bytes* and passed — nearly worthless, since the parts are deflated and a string is absent from compressed bytes almost by construction. Decompressing each part and asserting per part turned one green test into three failures: **`w14:docId`** (Word writes the per-document GUID in *both* namespaces at once, and the rule named only `w15`), **`w:rsid` as a standalone element** inside every `w:style` in `styles.xml` — reached by neither the attribute rule nor the `w:rsids` container rule — and the generalisation, since Microsoft versions its namespaces (`w14` 2010, `w15` 2012, `w16` 2021) and patching one sibling leaves the next to be found the same way. A test now scans every identifier-shaped name in the corpus and requires each to be ruled or recorded as content, so a `w16:` sibling fails a test instead of shipping. Tracked changes and comments are **refused, not removed**: accepting all revisions changes what a reader sees with markup on, which is a content-preservation failure wearing a scrub's clothes. Details in [`docs/p3_documents_plan.md`](docs/p3_documents_plan.md) §2.11.

**Measured (M11): which half of a DOCX still names its producer.** A DOCX has two producers in one file, so its A2 cell reports them separately — see the DOCX footnote above for the result. Three of the plugin's features turned out to be **measuring something other than their names**, all caught by the first run before any cell was published: `level_class` was reporting *part size* (a ZIP stores raw deflate, so the recovered level class narrows as a part grows — every file was compressed at level 6 regardless), `entry_order` stopped measuring ordering once our writer sorted (the sequence became a pure function of which parts exist, reporting the document model through a packager-shaped hole), and `entry_set` was in the wrong channel altogether, since which parts a package contains is the document program's decision, not the zipper's. Without those fixes the published cell would have claimed the packager channel still leaks after F1, on the strength of a size artifact and a misfiled key. **The fingerprint guard failed first, and the corpus was what was wrong**: it reported the complete central-directory records of two parts, CRCs included, because `diverse_inputs` wrote the same three-part package every time with only the paragraph text varying. The guard was right. Varying the *part set* fixed it, and the guard then passed on ten short declared constants with **no broad skeleton declaration of the kind PDF needed**. A test reproduces the undiverse corpus and asserts it still trips the guard, so the pass cannot quietly become vacuous. Details in [`docs/p3_documents_plan.md`](docs/p3_documents_plan.md) §2.12.

**Measured (M12): the claim this project had been repeating is wrong.** `CLAUDE.md` carried, from published research, that **OOXML RSIDs survive every scrubber including MAT2**. It had never been measured here. Measured now on two corpora — a synthetic package and a real Word document, with the control asserted first — **MAT2 0.14.0 clears every RSID**. What it leaves is the family nobody names: `w14:paraId` and `w14:textId` on every paragraph, and `w14:docId`/`w15:docId`, the persistent per-document GUID, in two namespaces at once. Our F1 clears all six. The paragraph ids are the sharper half, because they **travel with a paragraph pasted into another document** — they link *files to each other*, which is not an A1, A2 or A3 question at all. **ExifTool cannot write DOCX** (`Can't write DOCX files`), reported as a capability gap rather than a failure: a tool that declines leaves the file untouched, while a tool that writes an output still carrying the ids has told its user the document is clean when it is not. The claim was corrected rather than deleted — the useful version is that a scrubber can close the named channel and leave the unnamed one, which is exactly what the locus census exists to prevent. **E-DOCX-THUMB corrected a second expectation**: MAT2 strips `docProps/thumbnail.jpeg`'s own EXIF and **keeps the picture**. We drop the part, because a thumbnail can be *stale* — showing a paragraph the document no longer contains, the DOCX relative of PDF revision history — and because being a rendering it carries the typesetter's geometry in pixel space. Details in [`docs/p3_documents_plan.md`](docs/p3_documents_plan.md) §2.13; benchmark row in [`docs/benchmark.md`](docs/benchmark.md).

**Built (M13): DOCX F2, and four bugs found by checks rather than by reading.** The canonicaliser **was not idempotent** — a document declaring `mc` only to carry `mc:Ignorable` had both pruned as unused, emptying the attribute and dropping it, so `mc` was declared-and-unused on pass one and gone on pass two; canonical output that changes when canonicalised again is not canonical. It then **broke every real reader**: rewriting `<Types xmlns="…">` as `<ct:Types xmlns:ct="…">` is namespace-equivalent XML that LibreOffice rejects outright, caught only because the acceptance test is *does it still open* rather than *did we write a file*. The **content oracle was unsound** in a way that would have failed silently — a regex text extractor treats a canonical `<w:t/>` as an opening tag and swallows markup to the next run, reporting a text change that never happened, and the same regex was the harness plugin's `canonical_content`. And the **fingerprint guard failed the moment F2 landed**, reporting the whole `_rels/.rels` entry as our signature — genuine convergence this time rather than a corpus flaw, since every package's root relationships part declares one relationship once `docProps/*` is dropped, so it is declared the way PDF declares its empty document: generated, never transcribed. F2 also does what F1 refused — **accepting tracked changes and dropping comments** — which is a stated cost rather than a free win, since the markup view cannot be recovered ([limit #24](docs/limits.md)). Details in [`docs/p3_documents_plan.md`](docs/p3_documents_plan.md) §2.14.

### Phase 4 — HEIC (closed at F1)

A HEIC is **not one image in a box**: the picture is a grid of 61–95 HEVC tiles, and beside it in the same `mdat` sit the metadata items, a thumbnail and six auxiliary images, all addressed by **absolute offset** from one `iloc` table. Removing a metadata item therefore relocates everything after it — the `stco`/`co64` trap M4A taught, in its second guise, and M4A also taught what failure looks like: a file that parses perfectly and decodes to garbage. So the acceptance test **decodes** the image through an independent HEIF decoder rather than merely walking it.

Measured on six real iPhone photos: every one scrubs to **pixel-identical** output, and ExifTool sees **428 metadata tags before, 109 after** on the richest. Gone: `Make`, `Model`, iOS version, `DateTimeOriginal`, GPS latitude/longitude/altitude/timestamp, four XMP packets, the thumbnail, and every auxiliary image except the HDR gain map — 162 KB of depth maps, person mattes and style maps on the richest file, counted by what they *compose* rather than by the eight-byte descriptors that name them.

Also gone, and worth naming because it is a different species: Apple ships a **58 KB block — 3–5% of the file — describing the photo's own subject**. It records `PeopleRatio`, `SkinRatio` and a raster map of where the people are. Not a fact about the camera but a judgement a machine made about *what the picture is of*, computed on the phone and shipped inside it ([limit #30](docs/limits.md)). It is not a secret — ExifTool has always shown it — but nobody looks.

Three bugs on the way, each caught by measuring rather than reading. The walker first **refused Apple's `idat`-relative items** and so rejected all six real photos. Rebuilding `iprp` from the shared walker's `children` emitted an **empty `iprp`**, and libheif answered `Invalid input: No 'ipco' box` — a file that walked perfectly and decoded to nothing. And the report's own ExifTool cross-check caught the third on a real photo: keeping `ipco` whole left the file still advertising `urn:com:apple:photo:2019:aux:semanticskinmatte` **after the matte had been removed** — no longer carrying Apple's person-segmentation output, but still announcing that it had run.

**Then three more, found by building the corpus that CI was missing.** Thirteen tests needed a real iPhone photo and skipped everywhere else — and they were exactly the ones covering the hard paths, so CI was regression-testing the easy half. Writing a HEIC **byte by byte** (`heic_corpus.handbuilt()`, importing nothing from `src/`, with real HEVC tiles inside it so the test still *decodes*) meant first auditing what F1 actually emitted on the six real photos. It was not what the last milestone reported:

- **The auxiliary images were not being removed.** On an iPhone they are usually *grids*, like the photograph: `iloc` points at an 8-byte grid descriptor and the picture lives in twelve or thirty separate tiles. Dropping the item named in `iinf` removed the description and left every tile in `mdat` — **381 KB of a 1.17 MB photo, 707 KB of a 1.78 MB one**, on all six files, each tile individually decodable, with nothing left naming them so no tag-based check could see it. Removal is now computed on the `dimg` graph: an item survives only if a surviving image still composes it. The residual check that catches it had to be **connectivity, not naming** — and *undirected*, because deleting a tiled image deletes the reference that made its tiles tiles, and a directed walk then reads the orphans as top-level items and calls the file clean.
- **`iloc` was writing offset 0 for every item stored in `idat`.** The primary grid survived it (it is written first, so 0 was right) and everything beside it read the primary's descriptor instead of its own. The `stco` trap one level below `mdat` — and the channel it corrupts is one the pixel oracle cannot see, so six pixel-identical tests stayed green over it.
- **`grpl` entity groups** kept naming items that had been removed — the same dangling reference `iref` already guards against, in the box nobody looks at.

**And one decision reversed:** the **HDR gain map is now kept**. Unlike the mattes it says nothing about the subject — it is a half-resolution luminance map of the very pixels we preserve — and removing it renders the photo flat on an HDR display. Our own oracle cannot see that (libheif decodes the primary item and ignores the gain map), so the version that threw it away passed every pixel test we had; a decision no test can make is recorded in [`limits.md` #32](docs/limits.md) instead. Everything else auxiliary still goes, matched on the trailing component of the `auxC` URN because Apple has rewritten the prefix twice, with an unrecognised type failing toward removal.

Full write-up: [`docs/p4_media_plan.md`](docs/p4_media_plan.md) §4.

### Phase 4 — video: MP4 and MOV (F1, measured)

**Every iPhone video is QuickTime** ([plan §5–§6](docs/p4_media_plan.md)) rather than MP4, and each one carries more than the location everyone knows about:
- **six hidden tracks**, including **per-frame face detection** (where each face is, which way it is turned, an ID following it across frames) and a unique serial number per recording;
- **a stale second copy of the whole metadata block, exact GPS included**, written into bytes no player reads. This happens once every ten seconds of recording, or into a trailing `free` box for shorter clips. It was found in **6 of 6** clips measured.

`exiftool -all=` leaves that copy and then reads its own output as GPS-free. MAT2 refuses `.mov`, and on a renamed iPhone clip it crashes and leaves a 0-byte file. So F1 does not delete known fields and copy the rest: **it rebuilds the video data from only the chunks the kept tracks point at**, rewriting every chunk offset individually, so the leftovers are never written at all. On the real clips the output decodes frame for frame identically through ffmpeg. The GPS is gone from the bytes, not only from ExifTool's view. ExifTool's tag count drops from 7,405 to 118, and all of those are structural. An encoder that writes its settings *inside* the video stream (x264, as WhatsApp does) is kept at F1 and **named as kept** in the report ([limit #36](docs/limits.md)).

**The ISO side, measured first (M0, on a parallel branch)** — six desktop producers, and the finding that matters is about the measuring stick rather than about us: `exiftool -all=` on an AVFoundation-muxed MP4 reports *unchanged* and returns a **byte-identical** file that still carries its wall-clock creation timestamp and `Core Media Video` in every track handler. MAT2 does remove both, but by re-muxing through ffmpeg — a producer substitution rather than a deletion. Two structural traps are recorded before any handler code: one `-metadata location` writes the coordinate into **three** boxes, and a Keys-namespace `ilst` entry has **no name** (its type bytes are an index into `keys`), so dropping one `keys` entry renumbers the rest and silently relabels the survivors. Details in [`docs/p4_media_plan.md`](docs/p4_media_plan.md) §8.1.

**Built (M3, on that branch): and the decode test caught a bug in M4A.** The ISO-side F1 drops `udta` whole (so the GPS goes from `loci` as well as the tag list), zeroes the timestamps in **all three** header boxes — `mdhd` is the one a two-box implementation misses — blanks the `hdlr` track names, drops the pre-`mdat` padding, and patches `stco`/`co64` by however far the media actually moved. All six M0 producers decode to **byte-identical video** afterwards. The strip itself moved into `standards/isobmff.py` and is now shared with M4A rather than copied, which is the rule `CLAUDE.md` states and the reason arrived immediately: **M4A F1 had been leaking `Core Media Audio`** in any Apple-muxed file, because it was written before anyone measured handler names. **The decode test then found a worse one.** AVFoundation writes `mdat` with the 64-bit largesize header for a 17 KB box; our code *reconstructed* that header as 8 bytes instead of reading the 16 the file used, so the measured move came out **0** when the media really moved **−8**. Nothing was patched, the audio stayed byte-identical, the container parsed, the duration was right — and the file decoded to static. Shipped since Phase 2. Now the input offset is read rather than reconstructed, and the engine **follows every chunk offset from input to output and compares the bytes it lands on**, refusing rather than emitting a mismatch. Blanking the handler names then tripped the fingerprint guard, correctly — every output carries an identical `hdlr` box — so it is declared the way DOCX declares its empty `_rels`: generated from the code that writes it, bounded by a test that it carries no locus. Making that declaration *fit* needed two corpus fixes rather than a wider exclusion (language and duration, the fields either side of `hdlr`), which is DOCX M11's lesson repeated. Limits [#41](docs/limits.md) and [#42](docs/limits.md); details in [`docs/p4_media_plan.md`](docs/p4_media_plan.md) §8.6.

**Measured (M4, on that branch): which half of an MP4 still names its producer.** Nine structural features across four producers — and unusually the cell reports what F1 **closed** as well as what it left, because a cell listing only survivors reads the same whether a tier collapsed most of the channel or none of it. **Five of nine close at F1:** the padding, which boxes exist, the track handler names, the width of `mdat`'s length field, and whether timestamps were written at all. **Four survive** and they are coherent rather than arbitrary — `brand`, `compatible_brands`, `top_level_order` and `moov_before_mdat` are what the muxer *chose to be*, and a tier that deletes and zeroes cannot change that. Those four are the F2 specification, and the `not_tested` cells say so. The peer set includes a **second muxer implementation** rather than a second ffmpeg invocation (AVFoundation, pass-through so the coded video is identical), and the cell names the peer set it had, because a peer set that silently shrinks turns "we compared four producers" into a claim about three. **The fingerprint guard failed first and the corpus was wrong again** — it reported a 389-byte `trak` box as our signature because every hand-built track shared a duration, dimensions and timescale; third time this project has hit that (DOCX M11, M4A, here) and the fix is the same each time: vary the thing, do not widen the declaration. Rendering the section then caught the report quoting a cost for modes that do not exist — MP4 and HEIC are F1-only, and their deep-clean row said "costs you nothing at all". **And the peer set turned out to be platform-dependent in a way worth stating:** ffmpeg writes one set of handler names, one brand and one header width whatever its flags, so an ffmpeg-only comparison — which is what CI runs — cannot see three of the nine channels at all. The **verdict is the same either way**, verified by re-running with the producer removed rather than assumed, so no published claim depends on a Mac; what varies is resolution. A test contrasts the two peer sets so that claim cannot quietly go stale. Limits [#37](docs/limits.md), [#43](docs/limits.md) and [#44](docs/limits.md); details in [`docs/p4_media_plan.md`](docs/p4_media_plan.md) §8.7.

**Built twice, merged once (M12).** The two lines met on 2026-10-04. The QuickTime handler won, because it rebuilds `mdat` instead of copying it and so removes the stale copy the ISO branch had refused to face by refusing every `.MOV`. From the ISO branch came the M4A fix, the plugin and the A2 cell, two refusals (encrypted tracks, unmodelled header versions), 49 tests, and a report that now lists the ISO tags and `loci` box it removes — it had been removing them without saying so. **The A2 cell was re-measured on the merged F1 and came out the same:** the same five features close, the same four survive. A tenth, the track numbering, separates no one in this peer set but still counts the hidden tracks a QuickTime clip had, so it joins the F2 specification rather than being patched blind. The merge tripped the fingerprint guard once more, on a corpus whose `minf` sizes all shared their high bytes, and was fixed by varying them rather than widening the declaration. Details in [`docs/p4_media_plan.md`](docs/p4_media_plan.md) §9.

### Phase 4 — camera RAW (F1, TIFF family)

A raw file is the format where **nothing may move**: the sensor data sits at offsets the file's own tables record, and the camera's maker note — where the serial numbers live — also carries what the decoder needs. Zeroed whole, a Nikon file stops decoding and a Canon one loses its colour balance. So F1 never shifts a byte: it blanks values, removes directory entries in place and zeroes regions, maker by maker ([plan §10](docs/p4_media_plan.md)).

**M16, the writer, and an owner's name ExifTool cannot see.** The shared TIFF module learned the Olympus and Panasonic magic numbers, `SubIFDs`, five maker-note layouts read off real files (each maker writes a different header and counts its offsets from a different place), and three size-preserving writes. Blanking every identity field ExifTool names satisfied ExifTool on all five files — and a search of the **bytes** still found a Canon owner's name: a third copy inside a model-specific binary block ExifTool does not decode for that camera, so it reported the name gone. Every removed text value is now searched for across the maker note afterwards.

**M17, F1.** Dates in whichever directory a maker put them (Nikon puts one in IFD0, Sony repeats IFD0 in IFD1), the GPS directory, software and XMP, the time zones and dates kept inside maker notes (Canon records the time-zone **city**), and a DNG's embedded original file. The iPhone DNG's 5.4 MB **preview carries its own copy of the GPS**, written separately from the main one; it is cleaned through the Phase 1 JPEG keep-list with its colour profile kept, and padded back to its own length. Keeping previews was decided by measuring a viewer, not by taste: macOS QuickLook's thumbnail of the cleaned file is pixel-identical to the original's. ProRAW's sky **matte** — a map of the scene's content — is dropped, as HEIC's are. One trap found on the way: tag `0xC634` is Adobe's private block in a DNG but, in a Sony ARW, the pointer to the encrypted white balance the decoder needs, so it is removed in DNG only. Fuzzing then found the report crashing on a damaged preview the scrub drops anyway; fixed. **Panasonic RW2** followed (M18): it keeps its whole maker note, serials included, inside the EXIF of its preview rather than in the file's own EXIF, so cleaning the preview is what removes them. **Canon CR3** is the MP4 container around a still photo: its metadata is four little TIFF files inside Canon's own box, and its timed-metadata track carries the shot count **beside the white balance the decoder reads** — zeroed whole, the photo lost its colour — so it is edited record by record, and nothing moves because Canon's box records absolute positions. **Fujifilm RAF** keeps every identity value in its preview's own EXIF, and that EXIF cannot be dropped — stripped, the file no longer decodes — so it is cleaned in place; a search of the bytes then found the serial and a date again in Fuji's own header block, which ExifTool does not read, and those copies go too. All eight surveyed formats are handled; a maker note we have not measured is refused ([limit #46](docs/limits.md)).

## Usage
```
python -m src.scrub --fidelity F1|F2|F3 <input> <output>
```
`F1` bit-preserving · `F2` lossless re-encode · `F3` lossy re-encode. The tool dispatches by magic number (not file extension) and is **fail-closed**: any case it cannot fully scrub raises and writes no output. Before reading a video or M4A file it checks the machine has the memory the scrub needs (about 2.1× the file for video, 4× for M4A) and refuses up front if not; `--skip-memory-check` overrides that ([limit #38](docs/limits.md)).

Every successful scrub prints a **before/after report** of what it found and what happened to each field:

```
JPEG · F1 · 2.8 KB → 1.5 KB
  - EXIF:Make              TestCam
  - EXIF:GPSLatitude       51° 30' 0.00"
  - EXIF:DateTimeOriginal  2020:01:01 12:00:00
  - EXIF:IFD1 thumbnail    (614 bytes)
  - JPEG comment           secret comment leak
  - Photoshop/IPTC         1 IPTC field(s), 1 embedded thumbnail(s)
  - trailing bytes         (13 bytes after EOI)
  = kept: JFIF header
  17 removed, 1 kept
```

It shows what survived as well as what went — an MP3 at F1 reports its **LAME header** as kept, because that one cannot be removed without re-encoding ([limit #1](docs/limits.md)) — and it names each format's headline leak in the format's own terms: a PDF reports `3 revisions — earlier drafts are still in the file`, a Word document reports the editing-session id counts.

Then it stops taking our word for it. Every report ends with a reading by **ExifTool — a different implementation, not us** — because a handler bug that failed to remove a field would also fail to report it; both come from the same walker. The check can *disagree*, and that is the point of having it:

```
  Checked with exiftool 13.55 — a different implementation, not us:
    18 metadata tags before → 4 after
    gone entirely: ExifIFD, GPS, IFD0, IFD1, IPTC, Photoshop
    still reported: JFIF (4)
    none of the removed values appear in the output
  Check it yourself:
    exiftool -a -G1 -s out.jpg
```

If a value this report listed as removed is still readable in the output, the report says so loudly and tells you to treat the scrub as incomplete. The last line is the command to run yourself, because the whole block is only worth as much as your ability to reproduce it without us. `--no-verify` skips the check; `--no-report` skips everything.

Two limits stay in the wording. The report shows **what this tool can see**, so "nothing listed" never means "nothing was there" — which is exactly why the ExifTool block exists. And it necessarily **echoes the values it removed**, useful on a terminal and a disclosure in a log or a shared session.

## Approach in one paragraph
Metadata hides in redundant copies across coexisting standards (EXIF, XMP, IPTC, ICC), in embedded thumbnails and previews, in stale history left in the bytes, and in structural side-channels (file size, encoder ordering, quantization tables) — so naive field-deletion leaks. Feasibility is expressed per format as a **Pareto matrix** over fidelity tiers (F1 bit-preserving, F2 lossless re-encode, F3 lossy re-encode) and adversary tiers (A1 no-reference, A2 peer-corpus fingerprinting, A3 original-copy differential), validated by **differential testing**: scrub two content-identical, metadata-different files and treat any non-noise diff as a leak.

## Build order
Depth-first **by dependency, not popularity** — leaf formats before the containers that embed them. A shared spine (test harness + reusable EXIF/XMP/ICC/ID3 modules + dispatch) is built first, then JPEG/PNG → MP3 → PDF/OOXML → MP4/HEIC/RAW → executables → long tail. See `docs/implementation_plan.md`.

## Near-future goals
Phases 0–3 are closed and Phase 4 is under way, with **HEIC closed at F1**, **video measured at F1** and **camera RAW built at F1** for the TIFF family. Next, in order ([schedule](docs/schedule_report.pdf): media formats by 30 September, feature freeze 31 October):
- **Camera RAW: the A2 cell.** F1 works for all eight surveyed formats and the matrix is published (see Phase 4 above). What remains is the camera-*body* question, which needs a corpus of several files from two bodies of one model.
- **Video: the SEI experiment (M13)** — can x264's settings string be removed from the video stream without re-compressing it ([limit #36](docs/limits.md))?
- **MP4 F2** — the four channels A2@F1 leaves, plus renumbering the surviving tracks, are its specification ([limit #37](docs/limits.md)).
- **HEIC F2** — the spec already exists as A2@F1's named failure ([limit #33](docs/limits.md)): one canonical brand, one table order, one set of `iloc` widths, canonical item numbering, tiles untouched.
- **MP3: the second VBR header style (VBRI)** — not recognised. We had written that such files are refused; checked, they are not: F1 passes the header through (the same class of encoder trace as the LAME tag it keeps) and F3 removes it ([limit #7](docs/limits.md)).
- **Optional:** the JPEG E4 residual bound (primary-quantization trace after F3).

## Far-future goals
The full arc toward the deliverable — one tool that irreversibly scrubs files of arbitrary type:
- **Phase 3 — documents (PDF, then OOXML/Word): complete.** Both formats at all three tiers. The **RSID** problem turned out to be already solved upstream — measuring it rather than repeating it is what found the family that is *not* solved (`w14:paraId`/`textId`, `w15:docId`) — and PDF incremental-update history dies by construction in our rewrite.
- **Phase 4 — media & camera (HEIC → MP4 → RAW): HEIC is closed at F1.** Container item-table surgery, with the `iloc`/`idat` offset traps measured rather than guessed at, and the first format whose A2 result ships as a named failure that specifies its own fix. **MP4 and MOV** are built and measured at F1. They were not the cheap step they were expected to be: the camera writes a stale second copy of its metadata, GPS included, into bytes no sample table references, so F1 rebuilds `mdat` rather than copying it, and their A2 result also ships as a named failure that specifies its own F2. Then **camera RAW**, whose embedded full-size previews are the same "item with its own EXIF" shape HEIC establishes. **PRNU** sensor-noise stays a documented structural impossibility (removable only by destroying the image).
- **Phase 5 — executables**, then **Phase 6 — the long tail + whole-pipeline integration** (magic-number dispatch across every handler, recursive container scrubbing), including **decoy metadata (`--decoy`), default off** — spoofing rather than removal, on an axis orthogonal to F1/F2/F3: the fidelity tiers trade *content*, this trades *truthfulness*. It exists for the one attack the A1/A2/A3 ladder does not model — where **the fact of having been scrubbed is itself the leak**. Constrained, never random: a spoofed date must clear the file's own technology floor (a 2004 date on a file using object streams is falsified by its header), and the generator's distribution *is* a fingerprint across n outputs, so it ships only behind **E-DECOY**. Spec in [`docs/implementation_plan.md`](docs/implementation_plan.md).
- **Deliverable:** a professional **funding proposal** — technical content backed by the measured Pareto matrices, plus a cost plan.
- **End goal:** forensic unrecoverability validated by differential testing at **every** duplicate locus, per format, against the medium-tier (A2) adversary.

Every push to `main` and every pull request runs `.github/workflows/ci.yml`. It has six clearly-named jobs:

| Job | What it does |
|---|---|
| **Code quality** | `ruff` over the codebase (findings appear as inline annotations on the diff) plus `actionlint` over the workflow itself. Formatting drift is reported but never gates. |
| **Tests (Python 3.11 + 3.14)** | The full suite on both ends of the supported range, `fail-fast: false`. 3.11 is a hard floor — numpy/scipy/PyWavelets all require it; 3.14 is where a deprecation lands first. The middle versions were dropped after every failure to date reproduced identically on all four legs — the real variation in this project is the external toolchain, not the Python minor. |
| **Coverage** | Combines the coverage data from every leg (each writes its own file, so a branch reachable on only one interpreter still counts), then gates via [`scripts/coverage_gate.py`](scripts/coverage_gate.py). It holds *code the tests actually reach* to a floor, and lists files nothing reaches by name instead of letting them drag the average down — so landing a new format's scaffolding never fails the build, and never hides either. |
| **Published results still true** | Re-measures every Pareto matrix from scratch and fails if a published verdict no longer matches — see [`scripts/check_evidence.py`](scripts/check_evidence.py). Enforces *no claims without empirical validation* mechanically. |
| **QA report** | Builds and publishes the report. Runs even when everything else failed. |
| **CI** | The single required status check. Everything above is allowed to finish so the report always publishes; this job is the only one that turns the run red. |

The report itself renders **on the run page** (Job Summary) — no external site — and is written for a non-technical reader:
- a **verdict** (badges + one-sentence banner) and a five-second stage table with ✅/❌ and timings;
- a **Mermaid pipeline diagram** with every box coloured by what actually happened, so a red box shows exactly where it broke;
- a **coverage bar**, overall and file by file;
- results grouped into plain-English areas (*Hidden data removed*, *Picture and sound preserved*, *Made untraceable*, *Cannot be recovered*, *File stays valid*, *The tool behaves*), with a ✅-grid across Python versions;
- **what failed**, in readable words, with the file and line — also annotated inline on the pull-request diff;
- a per-format **capability table** read from the measured Pareto matrices, so a format the tool cannot yet do can never be claimed — and, since the guard reads the matrices off disk rather than trusting the report's own roadmap, one the tool *can* do can never go missing either (it did: a roadmap entry naming Word documents `ooxml` while their matrix is published as `docx` silently cost the report its entire Word section, and both the loader and the test agreed by being wrong together);
- the **"What we can't do yet"** section rendered straight from [`docs/limits.md`](docs/limits.md) — the single source of truth for every known limit, so the published report cannot drift from reality (tests enforce the wiring, and a missing document is reported loudly rather than rendering as a clean bill of health);
- the **before → after** scrub flow on real sample files.

A condensed version is posted and updated in place as a **PR comment**. Test results, coverage (including browsable HTML), the report and the scrubbed samples are all uploaded as artifacts.

Run the same checks locally:
```
python -m pip install -r requirements-dev.txt
ruff check .
python -m pytest -q --cov --junit-xml=pytest-results.xml
python -m coverage json -o coverage.json
python scripts/coverage_gate.py --coverage-json coverage.json --floor 82
python scripts/check_evidence.py --out evidence.json
python scripts/qa_report.py --junit pytest-results.xml --coverage-json coverage.json \
    --coverage-gate-json coverage-gate.json --evidence-json evidence.json \
    --summary qa-summary.md
```

To require a green build before merge, add a branch-protection rule on `main` requiring the **`CI`** check — that one job covers all the others.
